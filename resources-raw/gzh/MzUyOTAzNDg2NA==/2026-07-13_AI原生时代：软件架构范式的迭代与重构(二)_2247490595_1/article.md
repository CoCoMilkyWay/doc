7.提示词（Prompt）

提示词就是我们发给大模型的指令、提问或需求，是触发模型生成内容的原始输入。 

只写简单模糊的指令，模型很难精准匹配你的预期。

比如只说 “写一首诗”，模型无法确定体裁、主题、文风，产出结果随机性很强；

可如果把需求写得具体完整，写明体裁、主题、情绪风格，生成内容就会贴合想法。 

专门研究如何规范、清晰撰写指令来把控模型输出效果的方向，叫做提示词工程。

如今随着大模型理解能力持续提升，模糊指令也能被大致读懂，再加上撰写提示词本身门槛不高，现在专门钻研提示词工程的人已经变少。

提示词还分为两类：系统提示词与用户提示词。 

系统提示词由开发侧后台预先配置，用户无法看见，作用是定义模型身份、行为准则与输出规范；

用户提示词是使用者在对话框主动输入的具体问题、业务需求。 

举个数学辅导工具的例子：后台配置系统提示词，规定模型要扮演引导式数学老师，禁止直接给出答案；学生输入计算题提问，这就是用户提示词。

模型会结合两套提示词综合判断，遵循预设规则引导思考，而非直接给出最终结果。二者搭配使用，既能约束模型行为底线，又能响应每一轮用户的实际诉求。

与此同时，早年提示词工程是行业热点，核心靠人工打磨文字指令弥补早期大模型理解弱、上下文窗口小的短板，但随着通用大模型理解能力持续升级、百万级超大上下文普及，纯手写精细提示词的需求大幅降低，行业重心正在逐层迭代转移：

第一阶段从单纯打磨指令文字的传统提示词工程，转向**上下文工程**，不再纠结话术措辞，而是重点搭建完整信息环境，搭配 RAG 检索、对话历史、参考文档有序填充上下文窗口，保障模型拥有完整、准确的参考素材；

第二阶段延伸至驾驭层工程、循环工程，复杂智能体任务不再依靠冗长静态提示词约束流程，转而搭建自动反馈、自我修正的循环运行框架，由系统动态调整指令逻辑；同时提示词制作走向自动化，DSPy 等工具依靠评估标准自动迭代、筛选最优提示模板，摆脱人工反复试错，配套提示词版本管理、效果评测、成本管控的标准化工具链成为生产刚需；

除此之外提示词不再局限纯文本，多模态图文音混合提示成为常态，行业也形成分层落地方案，简单轻量业务用精简提示词，专业垂直场景结合提示词微调固化场景规则，减少长文本 token 开销，整体来看传统 “靠话术调模型” 的手工提示词工作占比持续收缩，提示词工程从零散技巧，升级为包含信息供给、流程管控、自动优化、模型适配的整套系统化 AI 开发能力。

8.大模型的外部能力延伸

大模型本身只有一个能力：基于已有训练数据，做文字预测。同时它有两个致命短板：**没有实时数据、无法操作外部世界**。

比如你问它今天天气、最新股价、数据库数据，它都答不了。因为它的知识是静态的、截止于训练时间，且如果不进行联网搜索、调用接口、执行计算。

想要弥补这个缺陷，就需要外部能力延伸，统称为大模型Tool。

**大模型Tool 的本质：一段可被调用的外部函数/能力**，比如天气查询、定位、店铺搜索、计算器、数据库查询。

Tool 只负责一件事：接收参数、执行外部逻辑、返回结构化结果。

一个核心分工：**大模型不会真正执行工具，它只会思考、判断、生成调用指令；真正调用工具、跑接口的是平台层。**

简单总结 Tool 的价值：**让只会说话的大模型，变成能查数据、能办事、能对接真实业务的模型。**

## 9.MCP 

## MCP，模型上下文协议：统一的工具接入标准。

假设有了基于大模型的Tool之后，马上会遇到一个巨大的工程痛点：工具适配成本太高。

不同大模型厂商，工具接入规范完全不一样：OpenAI 一套、Claude 一套、Gemini 一套。

这就导致：**同一个工具，你要写多套适配代码，对接不同平台，重复开发、极其低效。**

为了解决这个问题，行业推出了统一标准：**MCP（Model Context Protocol，模型上下文协议）**。

大家不用被学术名字吓到，MCP 本质非常简单：**一套所有 AI 平台都能通用的工具接入规范。**

MCP 带来的最大改变：

工具开发者**只需要开发、适配一次**，所有支持 MCP 的大模型、AI 平台，都可以直接复用这个工具，不需要重复开发、重复对接。

对于MCP来说，需要有**服务端和客户端**，在这里可以简单理解为，服务端是工具箱，里面是一系列工具，可以供AI去使用； 而客户端，则是与用户进行交互的AI本身。

  
以一个完整的 MCP 服务端与客户端示例来看，此案例假设用于查询 ETF 的收盘价。服务端使用 **baostock** 获取历史数据，并暴露两个工具：`get_date_range`（获取日期范围）和 `get_etf_close_price`（获取指定 ETF 在日期区间内的收盘价）。客户端通过 MCP 协议调用这些工具并展示结果。

server端示例代码：

```
#!/usr/bin/env python3
```

client端示例代码：

```
#!/usr/bin/env python3
```

在具体项目中使用时，首先执行 `pip install fastmcp baostock pandas mcp` 安装所需依赖；随后在终端运行 `python server.py` 启动服务端（默认以 SSE 协议监听 `http://127.0.0.1:8000`）；另开一个终端执行 `python client.py`，客户端会自动获取当前日期及 30 天前的日期，并调用服务端查询 `sh.510050`（上证 50 ETF）在该区间内的每日收盘价，最终在控制台打印前 5 条数据，同时将完整结果保存为 CSV 文件到当前目录。

10.Agent（智能体）

实际中可能会遇到这样的情况：向普通大模型提问分析实时股价、检索近期新闻这类需要外部实时信息的任务，模型只会回复无法获取实时数据，只能空谈理论，完全没法落地完成完整任务。

上面已经说过，纯LLM只是擅长输出观点、做解读的评论员，仅能基于存量知识做文字推演；而Agent是具备自主规划、调用外部工具闭环完成全流程任务的“执行总监”，能够真正落地解决完整业务诉求。

**LLM = 世界上最聪明的“评论员”**  
**Agent = 给你打工的“执行总监”**

_评论员负责“评头论足”，执行总监负责“把事办成”。_

Agent（智能体）在学术界有严格定义，但通俗的来看：

> **Agent是一个以大模型为核心大脑、具备自主规划、工具调用、循环执行、结果整合能力的自动化系统。它能理解模糊目标，自主拆解为可执行步骤，并通过多轮调用外部工具，最终完成复杂任务。**

  

_“Agent = LLM + Tool + 自主决策循环。缺了任何一个，都不叫Agent。”_

1）Agent最核心的特征就是具有自主规划（Planning）能力。

你给Agent一个目标（Goal），而不是给一套指令（Instruction）。

-   **传统编程**：if A then do B, else do C（每一步都是人写死的）
    
-   **普通LLM**：你问一句，它答一句（被动响应）
    
-   **Agent**：你说“我要去北京出差三天”，它自己列出：查机票→比价格→看天气→订酒店→规划行程→生成日程表
    

  

Agent自主规划的本质是Agent内部运行着一个**动态任务分解引擎**。收到目标后，它会：

1.  **理解意图**：用户真正想要什么？（而不是字面说了什么）
    
2.  **拆解子任务**：完成这个目标需要哪几个步骤？
    
3.  **排序依赖**：哪些步骤必须先做？（比如：订酒店前要先知道出差日期）
    
4.  **动态调整**：执行过程中如果某步失败，能否换方案？
    

举例说明：

**用户输入**：

> “帮我安排下周二去深圳出差的行程。”

**普通LLM回复**（只会给建议）：

> “建议您提前预订机票和酒店，查看当地天气，准备身份证件……”

**Agent的内部规划链**（假设你想设计开发一个行程安排相关的agent）：

```
目标：安排下周二深圳出差行程
```

_你只需要说'我要什么'，Agent自己说'怎么干'。_

_这是Agent和所有传统软件的分水岭。_

_也是我上篇文章中说的，要思考AI时代的软件开发必须充分理解和认识的概念。_

_2）Agent的第2个特征是可自主决策。_

Agent在执行过程中，会遇到无数个“岔路口”。它需要像人一样**实时判断**：

-   这个工具调用成功了吗？还是失败了？
    
-   返回的结果符合预期吗？还是需要重试？
    
-   当前进展到哪一步了？是继续执行，还是停下来问用户？
    
-   多个工具都可用，选哪个最合适？
    

以上面的案例为例：

决策场景

Agent会问自己的问题

**工具选择**

这个任务该用天气API还是爬虫？

**继续/停止**

数据已经拿到了，还需要进一步分析吗？

**重试/换方案**

主数据库连不上，要不要切到备份？

**求助/自主**

这个异常我没见过，要不要问用户确认？

**优先级排序**

机票快涨价了，先订票还是先查酒店？

**场景**：Agent正在帮你查“今天上海有什么好玩的活动”。

**第一次调用**：`search_events(city="上海", date="today")`

**返回结果**：`[]`（空列表，没有找到活动）

**普通LLM会怎么做？**（没有决策能力）

> “抱歉，没有找到今天上海的活动。”

**Agent会怎么做？**（有自主决策）

```
决策点1：为什么返回空？
```

_Agent的决策能力，决定了它是'一条道走到黑'的愣头青，还是'见招拆招'的老司机。_

_3）Agent第3个主要概念是：循环执行（loop）_

Agent不是在单次对话里一次性把所有工具调用完，而是采用 **“思考→行动→观察→再思考”** 的循环，直到任务完成为止。

这个循环在学术界有个经典名字：**ReAct（Reasoning + Acting）**。

```
┌─────────────────────────────────────────────────────┐
```

详细过程参考下表：

步骤

做什么

示例

**思考（Reason）**

当前状态是什么？下一步该干嘛？

“我查到了天气是下雨，用户没说要不要带伞，我应该再问一下，还是主动查雨伞店？”

**行动（Act）**

调用一个工具，或输出一段话

调用 `search_umbrella_shops(city="上海")`

**观察（Observe）**

工具返回了什么结果？

“返回了3家雨伞店：全家、罗森、7-11”

**（回到思考）**

拿到了雨伞店列表，接下来呢？

“用户只问了天气，要不要主动告诉他雨伞店？还是等他问？”

继续看下ReAct循环完整演示案例：

**用户**：

> “帮我看看最近的电影院有没有《阿凡达》的排片。”

**第1轮——思考**：

> “用户想看《阿凡达》，我先要知道'最近'是指什么范围，以及用户的位置。”

**第1轮——行动**：

> 调用 `get_user_location()`

**第1轮——观察**：

> 返回 `{city: "北京", district: "朝阳区"}`

**第2轮——思考**：

> “用户在朝阳区，接下来要查朝阳区电影院+阿凡达排片”

**第2轮——行动**：

> 调用 `search_cinemas(city="北京", district="朝阳区")` + `search_showtimes(movie="阿凡达", cinemas=[...])`

**第2轮——观察**：

> 返回 `[{cinema: "万达影城", time: "19:30"}, {cinema: "CGV", time: "20:00"}]`

**第3轮——思考**：

> “找到了2家，信息完整。但排片都是晚上的，用户可能想早点看，要不要追加问一句？”

**第3轮——行动**：

> 输出结果 + 追问：“找到了两家影院的晚间场次，如果您想看白天场，我可以再帮您搜。”

_Agent的ReAct循环，就像侦探破案：先想、再查、看结果、再想、再查……直到案子破了为止。_

  

4）Agent最后要做的就是结果整合

Agent执行完多轮工具调用后，手里会攒一大堆“碎片信息”：天气数据、航班列表、酒店评分、地图路线……它需要把这些碎片**拼合成一份完整、易读、有逻辑的输出**，而不是直接把原始数据堆给用户。整合能力包含三个层次：

层次

做什么

示例

**筛选**

去掉冗余、重复、无效信息

10家酒店里只推荐3家评分最高的

**组织**

按逻辑顺序重新排列

先说天气→再说航班→再说酒店→最后给建议

**呈现**

用人类友好的方式输出

表格？列表？分段文字？加粗重点？

**Agent收集到的原始数据**（碎片化）：

```
天气: 深圳, 周二, 晴, 28°C
```

**普通LLM输出**（只是罗列）：

> “我查到了以下信息：深圳周二天气晴28°C。航班有CA1303 8点……MU5391 10点……CZ3156 15点……酒店有如家280元、全季450元、汉庭200元……”

**Agent整合后输出**：

> **【出差行程推荐】**
> 
> **天气提醒**：周二深圳晴，28°C，适合出行，建议穿夏装。
> 
> **航班推荐（按性价比排序）**：
> 
> 1.  MU5391 | 10:00-13:00 | ¥980 ⭐推荐（时间好、价格最低）
>     
> 2.  CA1303 | 08:00-11:00 | ¥1200（早班，适合上午办事）
>     
> 3.  CZ3156 | 15:00-18:00 | ¥1500（偏晚，不推荐）
>     
> 
> **酒店推荐（综合评分+距离）**：
> 
> -   **全季酒店** | 评分4.7 | 距机场2km | ¥450 ⭐首选
>     
> -   如家 | 评分4.2 | 距机场5km | ¥280（预算之选）
>     
> 
> **建议**：推荐您选MU5391航班+全季酒店，中午抵达深圳，下午可自由安排。

_Agent的整合能力，决定了它是给你'扔一堆原始材料'的实习生，还是给你'一份完整方案'的高级助理。_

可能最终结果，大家在工作，生活中已经看的足够多了，但结合上面的过程，可以举一反三的反复思考这个最终结果背后的逻辑。

综合来看，Agent 之所以成为 AI 落地的核心抓手，核心在于它摆脱了传统大模型只能单纯输出文字的局限，能够自主拆解目标、串联多步骤工作，依托 SubAgent 实现任务并行，全天候承接重复、监控类工作，让规则、标准化操作、自动化校验机制得以落地生效，大幅释放人力。

但我们不能过度神化 Agent，它本身存在明显短板：

诸如任务循环中极易放大幻觉形成连锁错误、多轮执行易引发上下文过载、运行稳定性完全依附外部工具，且内部推理过程难以追溯定位问题。

也正因这些先天缺陷，Rule、Skill、Workflow、Scripts 等配套约束体系才不可或缺，相当于为能力强大但容易失控的 Agent 装上管控与兜底机制，保障复杂工程任务稳定、合规落地。
