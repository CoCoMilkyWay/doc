时间有限，特殊行情日，会在周末把所有数据跑完后分析。今天（713）的文章还是继续关AI产品设计开发的，先简单的小结下市场：

  

AI产业链是目前市场波动核心主线。近几个交易日板块走出极端拉锯行情：单日大幅冲高后快速回落、隔日又深跌反弹，大涨大跌交替成为常态。

  

如果参与AI 赛道，就需要了解和适应高科技，高成长赛道的高波动特性。一味的短线追涨杀跌极易反复亏损、持续交手学费；如果简单判定赛道风格彻底切换、行情见顶离场，也容易踏空中期主线，操作上需要提前制定清晰的仓位与止盈止损交易规则，不能仅凭单日涨跌主观预判趋势。

  

ai赛道经过一波“鸡犬升天”行情，所有龙头，虾兵蟹将都浮出水面了，做30元shkj的潜伏那种机会几乎没有可能了，所有看好的基本都在N倍以上“高位”，估值也相对行业或个股“高位”。这种情况对任何没有上车的人做决策是极其困难的，除非是但总那样有强烈，极致信仰又不差钱的（今天但总做客腾讯理财通谈了AI主题：不要错失一个伟大的时代。）。当然，这种k型分化的特殊行情对于在车上的，也不轻松，不能像开始那样，闭眼买，躺着不管就行，浮盈也是盈利，浮盈每天掉血或过山车，总归是影响自己心情的。所以在车上的就把精力放到仓位管理上，好好思考下长线与止盈的逻辑。

  

从外围市场看，当前全球AI龙头达子面临的筹码结构问题，也是A股多数高位AI标的共同痛点：估值与市值双重压制。

  

ai板块龙头市值体量庞大、阶段性估值处于高位，偏好高景气的纯成长型基金，持仓额度、风险约束都已触及上限，没有额外增量资金继续加仓推高股价。

  

存量资金博弈，缺少新增接盘方。被动指数基金、主流成长公募早在上半年完成重仓布局，场内只剩原有资金来回换手；没有新的长线资金入场承接，一旦集中兑现获利盘，很容易出现放量下跌。

  

原有持仓资金如纯成长型机构，是过去 AI 牛市的核心推手，只追逐 AI 高增速、科技高景气逻辑；目前普遍满仓，受个股持仓红线、净值波动限制，加仓空间基本封闭，只能做高抛低吸，无法持续托底行情。

  

潜在增量资金，如价值/收益型基金、家族办公室，资金风格和成长基金完全割裂，以往极少参与高估值科技股，选股标准侧重稳定现金流、持续分红、长期稳健回报；AI若能持续吸引长线价值资金进场，将彻底解决 AI 赛道 “缺少新买家” 的核心难题，缓解高市值、高抱团回调压力。

11.Agent skill

假设你手下有两个员工：

-   **员工A**：智商150，每次接到任务都自己琢磨怎么干，今天心情好按A方案，明天心情差按B方案。结果时好时坏，你永远不知道他会输出什么。
    
-   **员工B**：智商120，但手里有一本公司的《标准化作业手册》，接到任务先翻手册，严格按照规定的步骤、格式、标准执行，每次输出都一模一样。
    

**问题来了：作为管理者，你更愿意用谁？**

> 答案显而易见——**稳定压倒一切。**

### 如果Agent没有skill约束，那他大概率会是给咱们捅娄子的那个不靠谱的初级工程师。以一个“裸奔Agent”使用场景为例。

**场景**：你需要Agent每周一出一份《AI行业周报》。

**第1周**，你输入：

> “帮我出一份AI行业周报，包含：本周重要新闻、投融资事件、技术突破。格式：三段式，每段5条，带日期。”

Agent输出了一份还算满意的周报。

**第2周**，你输入：

> “同上。”

Agent输出了一份完全不同的东西——格式变了、条数少了、连风格都换了。因为它的“记忆”里没有上周的格式要求。

你只能重新贴一遍指令：

> “帮我出一份AI行业周报，包含：本周重要新闻、投融资事件、技术突破。格式：三段式，每段5条，带日期。跟上周一样。”

**第3周**，你发现上周的指令也不完美，还得加新要求：

> “帮我出一份AI行业周报，包含：本周重要新闻、投融资事件、技术突破。格式：三段式，每段5条，带日期。另外每条新闻后面加一句'影响分析'。”

**第4周，你崩溃了。**

因为你发现每次都要重复写这100多字的提示词，而且每次Agent的理解都有细微偏差。

  

_没有Skill的Agent，就像没有菜谱的厨师：每道菜都看心情做，客人永远吃不到同样的味道。_

如果只是周报还好，100字提示词勉强能忍。但真实业务的Skill往往极其复杂。

**举个代码审查Skill的真实长度**：

```
# Code Review Skill## 审查范围- 只审查本次提交的变更文件，不审查未变更文件## 审查清单（必须逐条检查）1. 命名规范：变量/函数名是否符合团队规范（小驼峰/大驼峰/下划线）？2. 注释完整性：所有公开函数是否有文档注释？3. 错误处理：所有可能抛异常的地方是否都有try-catch？4. 日志记录：关键操作是否有日志输出？日志级别是否正确？5. 安全性：是否存在SQL注入、XSS等安全风险？6. 性能：是否存在N+1查询、循环嵌套等性能问题？7. 测试覆盖：新增功能是否有对应的单元测试？8. 依赖检查：是否引入了不必要的第三方库？9. 配置文件：环境相关的配置是否已提取到配置文件？10. 向后兼容：API变更是否考虑了旧版本的兼容性？## 输出格式- 按严重程度分级：🔴阻断 / 🟡建议 / 🟢可选- 每条问题包含：文件路径 + 行号 + 问题描述 + 修改建议## 参考示例[此处附上一个完整审查示例]
```

**试想**：你不可能每次做代码审查时都把这段文字重新敲一遍。

即使你复制粘贴，还有两个致命问题：

1.  **遗忘风险**：你可能忘记贴某条重要规则
    
2.  **理解偏差**：每次粘贴的上下文里规则太多，Agent可能"选择性失明"
    

_虽然我们程序员都是ctrl + c仙人，但当你需要重复粘贴超过3次的时候，就不应该靠人力解决，这叫'工程债'，得用Skill来还。_

> **（Agent） Skill（智能体技能）是以Markdown文件形式固化的标准化工作手册。它把高频、固定、可复用的任务流程，预先写成结构化的操作规范，Agent在启动时自动加载，遇到匹配场景时按手册执行，无需用户每次重复描述。**

拆开看五个关键词：

关键词

解释

**Markdown文件**

就是普通的.md文件，用文本编辑器就能写，不需要编程

**固化**

写好一次，永久有效，不用每次重写

**高频固定流程**

只适用于重复性高的任务（周报、代码审查、会议纪要等）

**自动加载**

Agent启动时自动扫描文件夹，发现Skill自动"学会"

**按手册执行**

不是参考，是必须遵守（当然，还是软约束，后面Scripts才是硬约束）

##   

## Agent每天可能要扫描几十上百个Skill文件。如果每个都从头读到尾，效率极低。

所以Skill设计了**两层结构**：

1.  **元数据层（封面）**：让Agent快速判断“这个Skill跟我当前任务有关吗？”
    
2.  **指令层（正文）**：确认有关后，再深入读取详细执行步骤
    

_就像你翻一本书，先看封面和目录决定要不要读，而不是直接从头读到尾。_

**1）元数据层放在Markdown文件头部，使用YAML Frontmatter格式（用`---`包裹）。**

```
---name: 代码审查description: 按照团队规范对代码变更进行全方位审查，输出标准化审查报告triggers:  - "审查代码"  - "review code"  - "代码检查"  - "CR"---（下面是正文）
```

字段

作用

示例

**name**

技能名称，Agent用来识别和引用

"代码审查"

**description**

一句话说明这个Skill是干什么的

"按照团队规范对代码变更进行全方位审查"

**triggers**

触发词列表，Agent匹配用户输入时使用

"审查代码"、"review code"

**匹配逻辑**：

当用户说“帮我review一下这段代码”时：

1.  Agent扫描所有Skill的元数据层
    
2.  发现 `triggers` 里有 "review code" → 命中
    
3.  加载该Skill的完整指令层
    
4.  按照手册执行
    

_元数据层解决的是'选哪个Skill'的问题，指令层解决的是'怎么执行'的问题。_

2)指令层是Skill的核心，包含四个部分：

部分

内容

目的

**目标（Goal）**

这个Skill要达成什么结果

让Agent明确“做成什么样算完”

**执行步骤（Steps）**

按顺序列出所有操作

让Agent不遗漏、不乱序

**判断规则（Rules）**

遇到分支情况怎么处理

让Agent有决策依据

**输出格式（Output Format）**

最终产出长什么样

让结果可预期、可解析

一个好的Skill，应该让一个新来的Agent看完就知道怎么干，不需要任何额外解释。这就是'手册'和'便签'的区别。

**自动加载**

读取元数据层（YAML Frontmatter）建立索引；读取指令层（正文）准备执行

#### 多 Skill 命名建议

-   文件名建议使用**英文小写 + 连字符**，如 `code-review.md`
    
-   文件内 `name` 字段可使用**中文**，便于 Agent 识别和引用
    
-   一个 Skill 文件只描述**一个**完整技能，避免臃肿

#### _Skill 选择的本质不是技术问题，而是体验问题——让 Agent 在对的时候、用对的技能、以对的方式干活。_

## Skill的核心价值：

###   

### 价值一：消灭重复劳动（效率革命）

场景

无Skill

有Skill

周报生成

写100字提示词，5分钟

说"出周报"，3秒

代码审查

贴10条规则，3分钟

说"review代码"，2秒

会议纪要

说明格式要求，2分钟

说"出纪要"，2秒

部署检查

逐条核对，10分钟

说"检查部署"，5秒

_Skill把时间还给'创造性的思考'。_

###   

### 价值二：稳定输出质量（质量兜底）

-   无Skill：质量取决于**临场发挥 + 提示词质量**，时好时坏
    
-   有Skill：质量取决于**Skill设计质量**，次次一致
    

_kill把质量下限从'碰运气'变成了'可预期'。_

###   

### 价值三：知识沉淀与传承（团队资产）

-   老员工离职 → Skill还在，新Agent上手即用
    
-   规范升级 → 修改一个文件，全员Agent自动更新
    

_Skill不是写在Wiki里落灰，而是嵌入Agent的执行流程里。_

###   

### 价值四：行为可审计（工程基础）

Agent的异常行为可追溯：

1.  加载了哪个Skill？
    
2.  哪条规则导致该输出？
    
3.  是Skill写错，还是Agent执行偏了？
    

_Skill是Agent行为的'说明书'，也是事后追责的'证据链'。_

仅当次对话

_Skill很强大，但Skill不是万能的。_

_它本质上仍是‘软约束’：是一本手册，不是一副手铐。我们经常会遇到大模型调用skill时总不是那么一帆风顺，结果可能也不能保证软件时代百分百的可见结果。技术特效上如__Agent上下文太长时可能遗忘规则，用户指令冲突时可能优先听用户的，偷懒时也可能跳过某些步骤。_

_更关键的是，Skill的质量决定了执行的质量：步骤模糊、缺少示例、规则自相矛盾的Skill，比没有Skill更可怕，它会系统性地输出错误结果。而且Skill只能覆盖已知的、高频的、固定的流程，面对从未见过的新任务，它依然无能为力。_

_正因为这些局限，Skill只是工程保障的起点，不是终点，技术上需要用Workflow来规范流程、用Scripts来做硬性门禁，真正实现‘说到必须做到’。_
