1.低时延网卡不是只有AMD Solarflare

目前在高频交易需求下，使用的低时延网卡主要是3大选择：

-   AMD旗下Xinlinx的低延迟网卡：Solarflare X2522/X3522/X4系列。
    
-   NVIDIA旗下Mellanox（迈络思，现被英伟达收购，英伟达收购主要目的是通过多台GPU服务器如何通过最佳的网络解决方案构建超级“计算机”）：Mellanox ConnectX-4 LX。
    
-   Cisco旗下Exablaze：X10/X25
    

  

具体要选择那个，网络上有一些对比的文章，实际中都需要自己按自己的其他硬件的适配性，业务场景的用途等前提条件选择，并在具体的应用场景下测试其最终的性能表现。

2.AMD Alveo和AMD Solarflare

AMD Alveo和AMD Solarflare是AMD公司推出的两款不同类型的网络硬件产品。

它们在功能、应用场景和技术特点上存在明显区别。简要了解下AMD Alveo系列加速卡，目前常用的主要为U50和U200。

![](assets/001.png)

AMD Alveo属于计算加速卡，基于FPGA（现场可编程门阵列）技术，主要用于加速数据中心、高性能计算、人工智能、机器学习等领域的复杂计算任务，提供灵活的硬件加速能力，可针对特定算法和工作负载进行定制化优化。目前实际高频交易场景会使用其大规模计算加速的技术特点，把行情解码程序直接烧在AMD Alveo卡上。

以恒生电子子公司NanoExpress的行情解码方案为例

-   **网络版** 适合于用户对性能要求不高，面向中低频交易的交易系统。可大幅减少成本投入，用户无需额外购买FPGA板卡，可通过交换机转发给无限多的用户，板卡安装于专用的解码服务器上，数据通过网络（交换机）分发给各用户，支持一对多的用户使用场景，只要交换机的分发口数足够，不限客户数量。
    
-   **本地版** 适合于用户对行情性能有极致的追求，面向纯高频的交易系统。缺点是每个客户需单独采购一张FPGA板卡，一张FPGA板卡仅支持一个客户使用。行情解码在纳秒级完成，省去解码后数据网络传输的延时，将用户收取行情数据延时降到最低。

AMD Solarflare是网络适配器（网卡）产品，采用定制的低延迟ASIC芯片，专注于提供低延迟、高吞吐量的网络连接解决方案，主要用于满足数据中心、金融交易、实时数据分析等场景对网络性能的严格要求，强调网络数据传输的效率和稳定性。

简单来说，AMD Alveo是面向计算加速的硬件平台，侧重于提升复杂计算任务的性能；而AMD Solarflare是专注于网络连接的适配器，致力于优化网络数据传输的效率和稳定性。

3.Solarflare X4 **CTPIO**

上篇文章忽略了这块，Solarflare X4的核心创新在于其**CTPIO（Cut Through Programmed Input Output）技术**。这项技术允许数据包在尚未完全通过PCIe总线时就开始传输，大幅减少了处理延迟。传统网卡需要接收完整数据包后再进行处理，而CTPIO技术实现了近乎实时的传输-处理流水线。这个目前在处理开盘前的行情峰值中会有使用场景。

4.co-location

目前国内几个证券和期货交易所均设有专属服务器托管中心，比如上交所外高桥上证通托管机房、上交所金桥托管机房、深交所南方中心深圳通托管机房、东莞新机房等。期货交易所所处的张江、通联、农商行机房等。但因为受限于场地、电力等基础设施局限，目前往往是供不应求，越好的机房和机柜位置基本都要排队。

此类托管机房的机柜资源仅向证券、期货公司开放租用权限，相关机构需通过自有采购或客户指定配置采购的方式配备硬件设备，并搭配自研/外购软件系统，为终端客户提供交易相关服务。  

对于量化私募、高频交易（HFT）公司及自营交易团队等高端程序化交易主体，可通过向证券、期货公司申请的方式，获取托管机房内的机柜空间与网络资源。将自有交易主机或指定配置的定制化设备，在证券、期货公司许可后部署于租用机柜内，通过物理距离上的极致贴近交易所交易主机，实现交易指令传输与行情接收的低延迟优化，契合高频交易、量化策略对执行效率的核心诉求。

交易所数据中心会确保使用Co-location的客户无论将机器托管在交易所内的任何位置，都是通过相同长度的电缆传输、相同的延迟时间。比如实际中大家可能都希望自己的服务器能和交易所的行情服务器、撮合服务器物理上越近越好，但交易所托管机房内在任何位置的机架到核心行情或撮合服务器都使用相同长度的光纤，确保各个位置都具有相同的网络延迟。

4.量化投资中的低延时

围绕A股的证券、股票相关的高频交易场景下需要考虑低时延，在web3交易中，因为存在大量的跨市场套利机会，更需要考虑低时延。

套利的核心取决于两点，第一点是延迟，如果我们的策略能保证最先成交，则可以确定赚取利润；其次是策略，好的策略能带来超额的收益，当然这点主要取决于算法的优劣。

其中技术硬件层面延时可概况为网络层面和服务器层面：

-   网络层面的延迟：发起一笔交易时，耗时最长的是网络阶段。
    
-   服务器层面的延迟：
    

-   第一个是计算的延迟，因为策略基于实时行情做计算，如果算出的结果更快，则抢占了套利先机；
    
-   其次是在主机内数据包传输的优化。
    

  

5.行情解码方案

1)问题引入

前面文章中介绍过如果策略依赖低时延，则行情输入是第一道卡。

量化投资交易中涉及到大量股票的level2行情（相对每只股票3秒的快照行情，逐笔委托，逐笔成交数据量大，且需要进行处理），从接受和处理上都要快。

早上9.25集合竞价结束会批量发送逐笔数据，这时候一般压力较小，而9.30集合竞价开始那一刻，因为集合竞价未成交的订单加其他申报单，会出现短暂的行情高峰，行情解码端也会出现些许延迟，然后通过TCP或UDP组播方式到策略所在的服务器应用端程序，行情延时会加大。所以一般策略考虑都延时及行情滚动窗口数据完整性，可能会从9.31、9.32，9.33等时间点才开始正式开始策略运行。因此，针对行情，重点解决的是大量股票或期货合约下的接收处理问题、开盘前的行情峰值等特殊情况以及行情的异常监控等。

而针对交易场景，前提都是基于证券或期货柜台的SDK报盘，况且特别是股票高频策略并不是大家想象的微秒级、毫秒级不停的报单，虽然信号基于快照或逐笔（OB）来驱动实时计算，但并不是每个信号都需要下单，信号还需要根据策略条件、风控等逻辑，最终产生的交易订单相对行情，吞吐量非常小，且出现峰值的场景也比较低。比如A股票可能9.40产生了交易，后面一直没有符合的信号产生订单；B股票可能9.41产生了信号及订单，可能几秒后马上出现符合的信号，都是不定频的。因此，针对交易，重点是解决单笔交易的全链路延时（包括委托上行，委托确认的下行，成交回报的下行，以及多论证柜台的撤单速度，特别是如果有批量撤单场景，需要重点测试。）

以行情为例，传统的基于软件的行情信息系统，信息的解析一般经过网络层数据获取、协议层数据解析、应用层数据处理等过程，在操作系统和协议层面，存在毫秒级别的上下文切换和软件处理延时，由于操作系统的进程调度和CPU主频的动态调整机制，这种延时还具备一定的不确定性。所以对于行情信息延时的优化也从软件层次的优化逐步转移到基于硬件实现的加速方案。

2)行情协议

FAST（FIX Adapted for Streaming，适配FIX）是全球金融企业联盟（FPL）于2005年提出的面向消息流的压缩、编码与传输标准。其核心技术逻辑在于：利用消息流中前后消息的字段数据关联性实现数据压缩，并针对不同类型二进制字段采用高效二进制编码方案，从而显著提升压缩率、降低传输数据量。

在国内金融市场，上海证券交易所现行Level-2行情系统已部分集成FAST技术，在优化消息尺寸、节省网络带宽、降低行情传输延迟等关键指标上取得了良好的实际应用成效。

然而，FAST协议对下游用户的解码开发构成一定技术挑战。当前行业主流的行情解析方案仍依赖传统服务器CPU的软解析模式，主要通过调用mFAST、openFAST（之前实际测试下来差不多在百ms的延时，如果不特殊处理。）等开源库实现FAST码流的解码处理。该模式存在两大核心痛点：

1.并行化处理难度高：FAST数据采用流式排布结构，前后数据关联性强，导致CPU多线程并行处理难以有效落地，无法充分利用多核算力；

2\. 解码效率与资源占用矛盾：CPU的处理模式相对固定，缺乏底层细颗粒度的操作调度能力，不仅造成FAST软解码延迟偏高，还会占用大量CPU负载，成为制约行情解析系统性能提升的关键瓶颈。

提到协议还有一个：STEP（Securities Trading Exchange Protocol）协议。

其基于国际主流金融信息交换标准的FIX（Financial Information eXchange protocol）协议，根据行情数据的流式处理特征，进行了FAST（FIX Adapted For Streaming）编码压缩。

一方面，该协议定义了各种字段和运算符，用于标识特定的股票及其定价。另一方面，FAST编码带来的流式数据压缩机制，可大幅减少带宽，但也显著增加了数据解析的复杂度。在对协议解码的时候会用到。

6.关闭超线程

超线程（Hyper-Threading，HT）是英特尔于 2002 年推出的一种同步多线程硬件技术，属于 CPU 高效利用资源的经典方案，AMD 的类似技术虽称为对称多线程（SMT），核心逻辑与超线程基本一致。

普通CPU物理核心在处理任务时，常会因内存访问延迟、分支预测失误等出现执行单元闲置的情况，超线程技术正是针对这一问题设计。

其核心逻辑是在单个物理核心内复制两套独立的架构状态，包括通用寄存器、程序计数器等线程执行必需的状态信息，但共享算术逻辑单元（ALU）、浮点运算单元（FPU）以及 L1、L2 缓存等核心执行资源。这样一来，一个物理核心会被操作系统识别为两个逻辑核心，当一个线程因等待数据等陷入停滞时，另一个线程可立即占用空闲的执行单元继续工作，从而让核心资源始终保持高效运转。比如当线程 A 等待内存读取数据时，线程 B 可利用同一核心的整数运算单元执行计算任务，避免资源浪费。

超线程的性能提升并非线性增长，也远不能等同于增加同等数量的物理核心。实测中，它通常能为系统带来 10%-30% 的性能提升，其具体效果取决于应用场景。

在多任务并行、高延迟操作场景中表现突出，比如服务器处理大量网页请求、数据库并发查询、虚拟化环境中分配多个虚拟机任务等场景，能显著提高吞吐量；但在单线程密集型任务或两个线程高度争抢同一核心资源的场景下，效果会大打折扣，甚至可能因资源竞争出现性能下降，例如部分依赖浮点运算的科学计算、未针对多线程优化的单机游戏等。

比如在对延时抖动要求极高的高频交易场景中，超线程的逻辑线程共享资源会引发资源竞争，导致行情解析、订单发送的延时不稳定，因此该场景常需关闭超线程；此外，部分仅针对单物理核心优化的程序，以及对单核性能要求极高的特定科学计算任务，超线程也难以发挥作用，甚至可能拖慢运行速度。

基于此在高频交易服务器上一般要关闭超线程，Threads per core：每个核心的线程数（Intel CPU默认为2）；将 Threads per core 改为 1 即关闭超线程。

7.绑核（**CPU亲和性**）

同样，在高频交易程序运行时，为避免操作系统将高频交易线程在不同核心间切换，减少线程上下文切换开销（单次切换可能达数十微秒）。则需要对程序运作在指定的CPU核心上。确保交易线程独占CPU资源，避免被其他任务干扰，提供更稳定的性能。

另外线程固定在特定核心后，可长期占用该核心的 L1/L2 缓存，减少缓存失效与数据重加载耗时，可以提升缓存命中率；并且可防止其他进程（如系统服务、非核心业务）抢占高频交易程序的核心算力，确保关键路径的执行优先级。

特别是在多路CPU服务器上，访问“本地”内存和“远程”内存的延迟差异很大。绑核可以确保线程和其使用的内存位于同一个NUMA节点内。

绑核需要绑定物理核心，而尽量不能绑逻辑线程。

所以一般需要先关闭超线程后再绑核，这样绑核效果最纯粹，无资源竞争风险。

另外也可将高频交易核心线程与系统进程、非核心业务线程绑定到不同的物理核心，通过操作系统配置（如 Linux 的 cpuset）实现核心资源隔离。

启动程序时绑核命令如下：

```
taskset -c 0,1 ./my_hft_program
```

该命令指把自己的高频程序绑定到cpu ID为0，和1上。通过numactl -H查看CPUID。

![](assets/007.png)

对运行中程序也可以绑核，一般会在测试时使用，大多数还是程序启动时直接绑定：

```
taskset -cp 0,1 <pid>
```

平时开发程序的时候，会在代码中实现绑核操作，使用程序的时候在配置文件中指定要绑核CPU的ID即可。对于多线程程序，需要在线程创建后，在每个线程中分别设置。另外一些第三方库（如Intel TBB）提供了设置CPU亲和性的接口，可以方便地在多线程程序中使用。

```
#define _GNU_SOURCE
```

绑核并启动程序后，使用perf、mpstat等工具监控绑核后的性能，确定绑核是否有效。也可以用ps命令，打印出来后查看 PSR列，确认每个线程所在的CPU核心编号。

```
ps -eLo pid,tid,psr,pcpu,comm | grep -E ‘(my_hft_process|PID)’
```

实践中有时候不是简单的如上一个taskset命令这么简单，往往需要一个完整的绑核方案。

在系统启动时，通过内核参数`isolcpus`隔离一组核心，专供高频交易程序使用。例如，在GRUB配置中增加，然后重启系统。这样，操作系统不会在这些核心上调度其他任务，除非显式地指定。

```
isolcpus=0,1,2,3
```

将关键的交易线程绑定到隔离的核心上。

如果有多路CPU，考虑NUMA架构，尽量让线程在同一个NUMA节点上运行，避免跨节点访问内存。

将网络中断（例如网卡IRQ）也绑定到隔离的核心，确保网络数据包处理与交易线程在同一个核心，减少跨核心通信。

使用`irqbalance`服务或手动设置中断亲和性，将网络中断绑定到指定核心。（这个测试过但未实践），生产环境之前，充分测试绑核策略，因为不恰当的绑核可能导致性能下降。

```
echo 2 > /proc/irq/<irq_num>/smp_affinity
```

还有个cset命令，cset工具可以更灵活地管理CPU集合：

```
cset set -c 0-3 -s my_set
```

在绑核的基础上，使用 `chrt` 命令或 `sched_setscheduler` 系统调用，将关键线程的调度策略设置为 `SCHED_FIFO` 最高优先级，以防止被其他普通（`SCHED_OTHER`）线程抢占。这个命令实际中测试发现没有效果，未查明什么原因。

```
chrt -f -p 99 <pid> # 将进程的调度策略设置为SCHED_FIFO，优先级99
```

综上，小结下高频交易程序运行时绑核的简单步骤：假设系统有8个核心（0-7），我们隔离核心0-3供交易程序使用。

-   修改GRUB配置，添加isolcpus=0,1,2,3，更新GRUB并重启。
    
-   启动程序，使用taskset绑定到核心0-3。
    
-   将网络中断绑定到核心0-3中的某一个（例如核心0）。
    
-   使用cset进一步隔离，确保系统任务不会在隔离核心上运行。
    

  

实际中行情SDK自身一般都支持绑核，需在配置文件中设置。极速柜台SDK也有支持绑核的，但一般只允许绑定一个（按acc角度），除此就是自己策略相关程序的绑核，先检查CPU的numa架构，以及CPUid情况，然后计划下不同程序绑定的CPUid，进行设置操作。

跨numa架构下，确保行情或交易线程和它要访问的数据（如网络缓冲区）在同一个NUMA节点上。例如，如果网卡插在CPU0对应的PCI-E槽上，那么处理网络包的线程最好绑定在CPU0的某个核心上。

验证隔离的方法有两个：

```
cat /proc/cmdline | grep isolcpus
```

输出中包含上面设置的参数。

另外使用 top 或 htop 命令，运行 top，然后按 1 展开所有CPU核心的视图。

观察被隔离的核心（例如核心2,3,4,5）的 idle 时间（%id）。在系统有普通负载时，这些核心的 %id 应该持续接近100%，而其他核心的 %id 则较低。这说明调度器成功避开了这些核心。
