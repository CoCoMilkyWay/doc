2010年，道指20分钟暴跌了1000多点，跌幅超过9%，随后马上反弹，市场迅速寻找了“元凶”之一，高频交易，当市场出现小幅下跌时，高频交易算法可能触发止损机制，导致大量卖单瞬间涌入市场，在市场波动时又快速撤单，加剧了市场的流动性枯竭，在快速交易和算法之间的相互作用放大了市场的波动。

2010年9月，美国证券交易委员会（SEC）和商品期货交易委员会（CFTC）发布报告，将闪电交易事件归因于高频交易的快速撤单和市场流动性不足。报告指出，高频交易算法在市场波动时的快速反应加剧了市场的下跌，但同时也强调事件是多种因素共同作用的结果。

和目前国内大多数结论一样，认为高频交易对市场的两个主要作用是：减少价差，提高流动性。

![](assets/007.png)

通过一个买苹果例子介绍了下做市商：Alice想买苹果，苹果市场“流动性”很好，可以很方便的买到苹果，但Alice没有资金，她想先把自己的火龙果卖掉，只是火龙果“流动性”不好。

![](assets/008.png)

因为没有流动性，她挂出去的火龙果订单挂单了6小时也没有成交，这个期间如果苹果价格大涨，她卖出的火龙果资金也不够用，所以她可能会发起撤单。

![](assets/009.png)

![](assets/010.png)

Carl 是一个交易算法（Trading Algo），它扮演了做市商的角色。Carl 愿意立即与 Alice 匹配她的龙果卖单，这样 Alice 就可以马上获得资金去购买苹果。

Carl 在与 Alice 完成交易后，会等待另一个买家 Bob 出现。当 Bob 出现并愿意购买龙果时，Carl 再将龙果卖给 Bob，完成整个交易过程。

![](assets/011.png)

Carl 被称为“做市商”，因为他促成了原本可能无法发生的交易。在金融市场中，做市商的主要职责是为市场提供流动性，即随时准备买入和卖出某种金融工具（如股票、债券或期货等）。他们的存在使得买卖双方能够快速完成交易，而不需要等待合适的对手方出现。例如上面的例子中，如果没有 Carl 这样的做市商，Alice 可能需要等待很长时间才能找到愿意购买龙果的买家 Bob。而 Carl 通过立即买入 Alice 的龙果，使得 Alice 能够快速获得资金去购买苹果。同样，当 Bob 出现时，Carl 再将龙果卖给他，完成整个交易链条。

尽管看起来 Carl 在这笔交易中没有直接获利（因为他只是以市场价格买入并卖出），但在股票市场中，做市商通常会通过“回扣”（rebates，返现）来获得收入。回扣是交易所给予做市商的一种激励，通常是每笔交易手续费的一部分。

尽管做市商通过提供流动性获得回扣，但他们也承担了显著的风险。

价格波动风险：当 Carl 买入龙果时，他需要等待合适的买家 Bob 出现。然而，如果在等待期间龙果的价格下跌，Carl 可能会面临亏损。例如，他以 10 元的价格买入龙果，但市场价格可能在等待期间跌至 8 元。价格波动是做市商面临的主要风险之一，因为他们需要持有资产直到找到合适的买家或卖家。

**流动性风险**：Carl 无法保证在需要的时候能找到合适的买家或卖家。如果市场上没有足够的买家 Bob 出现，Carl 将不得不持有龙果更长时间，这不仅会增加价格波动的风险，还会影响他的资金周转效率。做市商需要时刻评估市场流动性和交易对手的可靠性，以降低这种风险。

**市场不确定性风险**：市场的不确定性（如宏观经济事件、突发新闻或政策变化）可能导致资产价格的剧烈波动，进一步增加做市商的风险。例如，如果市场上突然传出对龙果不利的消息，Carl 可能会面临更大的价格下跌风险。

开始正式进入低时延主题。

在高频交易中，“快”是大家口头禅，但什么样的结果算快?，却没有一个固定的标准可以定义，而是随着技术的发展不断变化的。

过去，不断是极速交易的厂商还是量化市场的高频参与饿着，大家说起交易速度可能以秒为单位，但如今，大家对高频交易的速度的要求已经达到了微秒（百万分之一秒）甚至纳秒（十亿分之一秒）级别。（当然，国内市场中，实际能做到的有几个，做到了能只靠速度做出业绩的又有几个，就不得而知。而国外市场，速度一定以为着“盈利”。）

![](assets/013.png)

  

光在真空中的速度是每微秒300米（300m/μs）。这是一个物理极限，所以在高频交易中，即使是光速传输的信号，也会受到距离的限制。因此，交易系统的物理位置是“快”的一个核心因素，如果将高频交易系统（HFT rig）部署在自己的数据中心，即使网络速度再快，也会因为物理距离导致延迟。例如，从一个城市的自有数据中心到交易所的距离可能有几十公里，这意味着光信号需要几十微秒甚至更长时间才能到达。云端服务器通常位于公共数据中心，与交易所的距离更远，延迟更高。这对于高频交易来说是不可接受的，因为高频交易需要在极短时间内完成交易。

所以过去，国内外高频交易公司会尽量将服务器部署在靠近交易所的数据中心，以减少网络延迟。例如，将服务器放在交易所所在城市的同一栋楼或同一数据中心内。

随着竞争的加剧和技术的发展，仅仅靠近交易所已经不够了。如今，高频交易公司必须将服务器直接部署在交易所的机房内（colocation），甚至与交易所的交易系统共享同一机架（rack）。这样可以将延迟降低到最低限度，通常只有几微秒甚至更低。

在交易所内部部署可以最大限度地减少光信号传输的时间。例如，如果服务器与交易所的交易系统之间的距离只有几米，那么光信号的传输时间可以忽略不计。

![](assets/014.png)

在美国市场中，由于严格的市场监管，外部网络延迟（一系列因素）的差异已经被抹平。因此，真正的竞争现在存在于交易者的**技术栈**内部。

国内市场会感觉也越来越处于此情况下，当交易所速度提升上来，交易所的机房扩容提效后，证券公司的极速柜台不断提速后，且这些公开的基础设施参与者都能获取到时，需要和竞争者拉开差距，就需要在自己的“高频系统”中下苦功了。

一个能赚钱的产品（策略）需要有一个盈利的交易逻辑、强大的交易基础设施以及快速应对市场事件的能力之间找到正确的平衡。如果交易逻辑本身有误，或者反应迟缓，那么一切都无济于事，成败完全取决于自己高频交易系统的技术栈。

在高频交易领域，品牌几乎不存在——没有任何东西能阻止一个更聪明或更快的竞争对手抢走你的“市场份额”。所有行动都必须严格遵守市场监管规定——任何漏洞都可能导致巨额罚款！

这个理解几乎在目前国内情况几乎一样。

高频交易（HFT）中交易者面临的几个核心挑战：

市场行为无法准确预测：金融市场是复杂且动态的系统，受到无数因素的影响，包括宏观经济数据、政治事件、市场情绪、技术发展等。这些因素相互作用，使得市场行为难以准确预测。比如不确定性：交易者永远无法确定他们的交易决策是否完全正确，因为市场条件可能在瞬间发生变化。例如，一个看似有利可图的交易机会可能因为突发新闻或市场波动而迅速逆转。比如方向性风险：即使交易者对市场趋势有合理的判断，也无法保证他们的方向（做多或做空）是正确的。市场可能在任何时刻反转，导致交易者面临损失。

快速交易与快速止损的重要性：高频交易依赖于在极短时间内捕捉和利用市场机会。这意味着交易系统必须能够在微秒甚至纳秒级别上执行交易指令。如果交易方向错误或市场条件发生变化，交易者需要能够迅速反转交易并止损。这不仅需要快速的决策能力，还需要交易系统能够快速响应市场变化。例如，如果一个高频交易算法检测到某个股票的价格突然上涨，它可能会迅速买入，但如果价格随后立即下跌，算法必须能够迅速卖出以减少损失。这种快速反应能力是高频交易成功的关键。

永远不够“快”：在高频交易领域，速度的竞争是无止境的。交易者总是试图通过技术优化来减少延迟，提高交易速度。这是因为每一纳秒都很重要，在高频交易中，即使是极小的时间延迟（如几纳秒）也可能导致错过交易机会或增加交易成本。例如，如果一个交易机会在100纳秒内消失，而交易系统的延迟是150纳秒，那么这个机会就无法被捕捉。减少实时交易流程中的延迟可以显著提高盈利能力。反之，如果延迟增加，盈利能力可能会下降。这是因为高频交易依赖于快速捕捉大量微小的利润机会，而这些机会往往转瞬即逝。

本次演讲者来自qSpark公司，qSpark 是一家专注于高频交易和低延迟技术的公司，其核心竞争力在于开发高性能、低延迟的交易系统和基础设施。通过优化技术栈、减少延迟和提高系统效率，qSpark 为金融机构提供了在高频交易市场中竞争的工具和解决方案。

作者谈到了qSpark的低时延实践要点，结合AI详细解释下：

### **1\. 端到端内核绕过（End-to-end kernel bypass）**

-   **背景**：在传统的操作系统中，系统调用（如网络操作、文件操作等）需要从用户空间切换到内核空间，这会带来额外的延迟。对于高频交易，这种延迟是不可接受的。
    
-   **解决方案**：qSpark采用端到端内核绕过技术，直接在用户空间处理数据和操作，避免了系统调用带来的上下文切换和延迟。例如，通过使用用户态网络库（如DPDK），可以直接在用户空间处理网络包，而无需经过内核网络栈。
    
-   **优势**：显著降低延迟，提高系统的实时性和响应速度。
    

### 

### **2\. 避免上下文切换、排队和线程间数据传输（Avoid context switching, queuing and data transfer between threads）**

-   **上下文切换**：在多线程环境中，线程切换会消耗大量时间，尤其是在高频交易中，这种延迟可能导致错过交易机会。
    
-   **排队和数据传输**：线程间的数据传输和排队操作也会引入额外的延迟。例如，线程间共享数据需要同步机制，这会增加复杂性和延迟。
    
-   **解决方案**：qSpark尽量减少上下文切换，采用单线程或少量线程的设计，并通过优化数据结构和内存布局，减少线程间的数据传输和排队操作。
    

### 

### **3\. 确定性、静态代码流程（Deterministic, static code flow）**

-   **背景**：在高频交易中，运行时的动态决策会引入不确定性，导致延迟增加。
    
-   **解决方案**：qSpark采用确定性、静态代码流程，尽可能在编译时做出决策。这意味着：
    

-   使用模板编程技术（如CRTP，Curiously Recurring Template Pattern）来实现编译时多态，避免运行时的虚函数调用。
    
-   将配置参数通过模板传递，而不是在运行时动态读取。
    
-   使用静态数据结构，减少运行时的动态内存分配。
    

-   **优势**：减少运行时的分支预测错误和延迟，提高系统的确定性和性能。
    

### 

### **4\. 最小化缓存未命中和错误分支预测（Minimize cache misses and wrong branch prediction）**

-   **缓存未命中**：在高频交易中，缓存未命中会导致显著的延迟。qSpark通过以下方式优化缓存使用：
    

-   使用紧凑的数据结构，减少数据占用的内存空间，提高缓存利用率。
    
-   预热缓存（Cache Warming），通过模拟交易流程，提前将数据加载到缓存中。
    

-   **错误分支预测**：分支预测错误会导致CPU执行不必要的指令，增加延迟。qSpark通过以下方式减少分支预测错误：
    

-   使用简单的逻辑和线性代码流程，减少分支数量。
    
-   通过编译器优化和代码布局调整，提高分支预测的准确性。
    

### 

### **5\. 使用定制化数据结构（Use custom-tailored data structures for specific use cases）**

-   **背景**：通用数据结构（如`std::map`、`std::vector`等）虽然功能强大，但在高频交易中可能不够高效。
    
-   **解决方案**：qSpark根据具体需求设计定制化的数据结构，例如：
    

-   静态平面映射（Static Flat Map）：一种基于数组的映射结构，通过二分查找实现快速查找和迭代，适用于小规模数据集。
    
-   环形缓冲区（Ring Buffer）：用于高效的消息传递和数据存储，减少内存分配和释放的开销。
    

-   **优势**：这些定制化的数据结构在特定场景下可以显著提高性能，减少延迟。
    

### 

### **6\. 测量性能（It is not faster if you haven't measured it）**

-   **背景**：在高频交易中，性能优化是一个持续的过程，任何微小的改进都可能带来显著的收益。
    
-   **解决方案**：qSpark采用严格的性能测量方法，确保每一步优化都能带来实际的性能提升。例如：
    

-   使用高精度计时器（如纳秒级计时器）测量代码片段的执行时间。
    
-   对比不同优化策略的效果，选择最优的实现方式。
    
-   持续监控系统的性能指标，及时发现和解决性能瓶颈。
    

-   **优势**：通过精确的性能测量，确保优化措施的有效性，避免盲目优化。
    

###   

qSpark的开发方法专注于通过技术优化减少延迟，提高系统的实时性和性能。这些方法包括端到端内核绕过、减少上下文切换、确定性代码流程、优化缓存使用、定制化数据结构以及严格的性能测量。这些技术策略在高频交易领域尤为重要，因为它们直接影响到交易系统的速度和盈利能力。

1.Daterministic code flow and branching minimization

程序每个运行时操作都会带来性能损耗。而在分支预测错误的情况下，这种损耗会进一步加剧，意味着CPU周期被浪费。所以需要设计致力于创建一个确定性的、静态的流程，通过将开销转移到编译和初始化时间，来最小化运行时的分支。通过这种办法将尽可能多的决策和开销转移到编译和初始化阶段，来减少运行时的分支数量。这样做的好处是，虽然编译和初始化时间可能会增加，但运行时的性能会更加稳定和高效。

CRTP（Curiously Recurring Template Pattern）是C++模板编程中的一种通常采用方法和设计模式，它是指一个类（通常是基类）以其派生类作为模板参数的模式。或者说，基类是一个模板类，派生类在继承该基类时，将自身作为模板参数传递给基类。通过这种模式，基类可以访问派生类的成员，从而实现代码的复用和扩展。

通过使用CRTP，可以在编译期间将基类的行为特化到派生类中，而无需运行时的虚函数调用开销，使得在编译时实现静态多态性。演讲时提供了3个不同类似的代码实现：

示例代码1：

```
class order {
```

上面的代码示例有三个类：基类`order`，派生类`specific_order`和`generic_order`。基类`order`有一个虚函数`place_order()`，并提供了默认实现。`specific_order`重写了这个虚函数，而`generic_order`继承自`order`但没有重写`place_order()`。

`generic_order`没有实现`place_order()`意味着它直接使用基类的默认实现。在某些情况下可能合理，比如当存在一种通用的订单类型不需要特殊处理时。当然，这个在实际中肯定会存在一些风险，因为基类的默认实现如果遇到不适用的业务场景，那系统肯定会出现逻辑错误。

其中虚函数和纯虚函数的区别在于，纯虚函数没有默认实现，必须在派生类中重写。如果`order`类的`place_order()`是纯虚函数（即`virtual void place_order() = 0;`），那么`generic_order`必须实现这个方法，否则编译会失败。因此，使用纯虚函数可以强制派生类提供自己的实现，增加代码的安全性。

这段代码示例使用的是动态多态，依赖虚函数表，运行时解析函数调用。这种实现会带来一定的性能开销，比较适合运行时灵活性的场景。这个我们国内从事交易系统的同学肯定不陌生。
