# 4\. 核心模块设计详解

## 4.1 订单撮合引擎

该系统的核心是订单匹配引擎（hft-engine）。

它维护一个或多个内存中的限价订单簿，并按价格-时间优先级执行匹配逻辑。

目前，系统为每个交易品种实现一个集中式订单簿，买卖双方分开。

在 Java 中，系统引擎使用 Disruptor 环形缓冲区（RingBuffer）作为其输入通道。

外部组件（策略、客户端）将新订单、取消订单或替换订单作为 OrderEvent 消息发布到此环形缓冲区。

引擎具有一个事件处理程序，按顺序处理每个 OrderEvent。

在内部，系统使用价格排序的映射来表示账簿的每一面，该映射从价格水平到订单队列。

具体来说，系统使用 Java 的 <TreeMap> 来存储买价和卖价。价格以缩放后的整数（例如价格 \* 10⁸）存储，以避免浮点运算问题。LinkedList 中的每个条目代表一个单独的订单或子订单。

TreeMap 确保最优价格始终位于一端，并且插入/删除操作是按对数速度进行的。（注：为了进一步优化，可以使用像 Agrona 的 Long2ObjectHashMap 这样的原始树形映射，但对于现代硬件而言，Java 的 TreeMap 足以应对每秒数百万次的事件。）

匹配逻辑如下：

1.交易前验证：在撮合交易前，每笔订单都会根据交易前风险限额（规模、名义金额、允许的交易品种）进行检查。如果订单违反限额，则会立即被拒绝。

2.订单撮合：如果订单可成交（例如，买单价格≥最佳卖价，或卖单价格≤最佳买价），系统会从交易对手的订单簿中获取流动性。系统从最佳价格开始，遍历交易对手的TreeMap，匹配订单数量。对于每个价格水平，系统会尽可能多地成交，并更新已入库订单和已挂单。每笔成交的交易都会生成一个TradeEvent（包含价格、数量和交易对手信息）。

3.剩余交易处理：如果市价单或限价单在消耗流动性后仍有剩余数量，则该市价单将被取消，限价单将被放入交易簿。对于限价单，剩余数量将按其价格水平入队（添加到映射表中的链表）。

4.发布结果：每笔交易生成后，系统都会发布一个事件（通过 Disruptor 或内部回调），以便下游模块（风险、持久性、策略）可以处理成交。如果账簿上新增了订单（带有剩余），系统可能还会发布一个OrderBookUpdateEvent 事件，用于审计或数据分发。

由于引擎在单线程上串行处理事件，因此匹配过程中无需加锁。这种设计保证了事件的确定性顺序。

整个引擎逻辑封装在一个线程（或一个 Disruptor 事件处理程序）中。这避免了同步账本状态的复杂性。许多实际的高频交易匹配引擎都遵循类似的模式：每个市场（或每个符号组的分片）使用一个单独的“匹配线程”以避免争用。

系统支持标准订单类型：市价单、限价单、取消订单和替换（AMEND）指令。系统的匹配机制采用价格优先、时间优先的原则：先匹配最优价格，再匹配最早的订单。这与交易所常用的先进先出（FIFO）算法相符\[16\]。（一些交易所也提供按比例匹配，但本系统专注于价格优先、时间优先，如有需要可以扩展。）

## 4.2 风控管理模块

由于高频交易可能迅速造成亏损，系统实施了位于关键路径上的实时风险管理机制，同时设有交易前和交易后控制措施，即事前风控和事后风控：

交易前风险检查，是指每笔新订单在发送至交易引擎或交易所之前，都会经过一系列检查。这些检查包括：

-   数量限制：订单数量必须介于最小值和最大值之间。
    
-   名义金额限制：总名义金额（价格×数量）不能超过单笔订单的上限。
    
-   每日亏损限额：系统会跟踪每项策略/账户的损益，如果亏损超过每日阈值，则会阻止新订单。
    
-   持仓限制：系统对每个交易品种的最大持仓规模和总持仓规模实施限制。
    
-   订单速率限制：为防止订单提交失控，系统对每个策略或帐户每秒提交的订单数量进行限制。
    
-   价格检查：如果订单价格与当前市场价格严重偏离（例如超出可配置的价差），系统会标记该订单（“误操作”保护），并要求手动覆盖。
    
-   特定交易场所规则：有些交易所的规则比较特殊（例如最小价格变动单位、限制交易对），因此订单会相应地进行调整或阻止。
    

这些检查仅使用内存中的数据（当前持仓、盈亏、近期订单），且开销极小（单线程查找）。在许多市场，此类交易前检查是获得交易所准入的必要条件。例如，芝加哥联储指出，清算成员通常会设置价格和数量限制，以防止错误交易\[6\]。系统同样会在订单发送到任何交易场所之前强制执行这些限制。

其中交易后风险与监控，主要是指交易完成后，系统会立即更新持仓和盈亏情况。风险管理模块维护着一个内存表，其中包含每个交易品种和账户的实时持仓和按市值计价的盈亏信息。这使的系统能够触发相应的控制措施：

-   如果接近亏损限额，系统可以自动取消未完成的订单或停止交易。
    
-   这里还可以计算投资组合层面的风险价值或希腊字母（如果使用期权）（未来工作）。
    
-   系统还会监控运营损益、保证金使用情况以及跨交易所的风险敞口等综合指标。
    
-   如果出现异常情况（例如与某个交易所的连接中断），系统可以启动熔断机制：例如停止发送新订单，直到情况恢复正常。
    

由于风险模块共享 Disruptor 事件流，因此它可以实时查看成交和订单更新。系统在同一线程上处理交易事件时同步更新仓位，因此执行与风险影响之间不存在延迟。这种零延迟反馈循环确保不会出现超出范围的交易。

总体而言，风险管理流程运行在同一低延迟流水线中，每个订单的处理时间仅增加几微秒。它避免了关键路径上的任何数据库或外部调用，所有检查都在内存中进行。

## 4.3 数据处理模块

数据处理模块（hft-market-data）是该系统的一个关键组成部分。它负责连接交易所、订阅数据源，并在系统内分发标准化数据。其主要组成部分包括：

-   WebSocket 连接器：大多数加密货币交易所（例如 Binance、Coinbase Pro 等）都通过 WebSocket 提供实时数据流。我们有一个 WebSocketMarketDataClient 基类，并为每个交易所创建了特定的子类。每个客户端处理以下功能：
    

-   如有需要，进行身份验证（API密钥）。
    
-   订阅交易流和订单簿快照/更新。
    
-   将传入的消息（JSON 或二进制）解析为我们的 MarketDataEvent 格式。
    
-   检测和处理断开连接（自动重新连接并退避）。
    
-   管理心跳或ping/pong消息以保持连接。
    
-   将交易所特定数据（例如价格为 double 类型、时间戳格式）转换为规范字段。例如，某个交易所的连接器会将 JSON 交易消息转换为包含交易品种、价格、数量和时间戳的内部 TradeEvent。系统会将此 TradeEvent 发布到 Disruptor，供策略和本地订单簿（如果是模拟交易）使用。WebSocket I/O 使用 Netty 的 HTTP/WebSocket 管道来最大化吞吐量\[14\]。
    

-   TCP/UDP 数据流：部分交易场所提供基于原始 TCP 或 UDP 的低延迟二进制数据流。本系统通过基于 Netty 的服务器 (TcpMarketDataServer) 来支持这些数据流，并将其作为市场数据中心。在内部，系统可以使用 Aeron IPC 将市场数据多播到多个策略或组件。例如，系统定义了一个由 SBE 支持的MarketDataUpdate消息，并在进程内广播该消息：多个消费者线程无需复制即可读取相同的数据（使用 Aeron 可靠的多播传输\[4\]）。
    

-   规范化和时间戳：所有市场数据在接收时均会添加时间戳。为保证数据一致性，系统在网关处（发布前）将时间转换为 UNIX 纳秒。系统假设本地机器时间已通过 NTP/PPS 同步。数据已规范化为通用类型（例如 TradeEvent(symbol, price, quantity, timestamp)、BookUpdateEvent(symbol, side, price, size, timestamp)）。
    

-   数据分发：标准化后，事件数据会被放置在 Disruptor 环上进行分发。这意味着多个订阅者（策略、订单簿、分析工具）可以并行处理相同的原始数据，几乎不会出现争用。系统还可以发布到外部数据源：例如，下游 REST API 或内部仪表盘可以订阅实时交易和订单簿变更数据源。
    

-   回填和订单簿：为了构建本地视图，每个符号连接器在启动时通过 REST 获取快照，然后应用实时差异。系统使用 Agrona 的 AtomicBuffer 和直接内存结构将订单簿状态存储在堆外，从而降低 GC 压力\[10\]。传入的增量更新会修改内存中的订单簿。Disruptor 还可以将这些BookUpdate事件传递给感兴趣的消费者（例如，用于监控买卖价差变化的风险）。
    

总而言之，市场数据模块为系统其他部分提供低延迟、标准化的加密货币市场活动数据流。它将交易所特有的差异隐藏在统一的接口背后。

## 4.4 FIX 协议网关

虽然零售加密货币 API 通常采用 REST/WebSocket，但机构交易和一些交易所需要使用金融信息交换 (FIX)协议。系统的hft-fix-gateway使用 QuickFIX/J 实现了 FIX 4.4。它既可以作为客户端（通过 FIX 向交易所发送订单），也可以作为服务器（接收来自 FIX 客户端的订单）。

FIX协议网关设计开发的关键要点如下：

-   会话管理： QuickFIX/J 处理 TCP 会话、登录/注销、序列号和心跳消息等底层细节。我们为每个交易对手（交易所或客户端）配置单独的会话 ID。
    
-   消息转换：我们将内部的 Order 和 OrderCancel 对象映射到 FIX 消息（例如 NewOrderSingle、OrderCancelRequest 等）。反之，当我们收到 ExecutionReport（FIX 的成交报告）时，我们会将其转换为内部的 ExecutionReportEvent 并发布。此转换层确保核心引擎与协议无关。
    
-   延迟考量：出站 FIX 消息由 QuickFIX/J 异步排队。在优化配置中，每条消息的延迟通常在几十微秒左右\[15\]。我们配置 FIX 引擎使用高性能持久化方案（用于存储传输中消息的内存存储和基于文件的备份），并尽可能重用消息对象以减少垃圾回收 (GC)。
    
-   可靠性： FIX 连接包含序列恢复功能。如果系统重启，QuickFIX/J 可以从存储中重放连接，或请求交换机重新发送连接。内存中的风险和状态随后会被重放以恢复上下文。
    

拥有 FIX 网关可以连接到加密货币期货交易所（例如通过 FIX 连接的芝加哥商品交易所的比特币期货）或提供加密货币交易服务的经纪商。它还提供了一个标准化的机构接口。

## 4.5 持久层设计

尽管关键交易路径避免了任何磁盘或网络延迟，但系统仍然需要持久存储来进行审计和分析。为此，hft-persistence 模块使用 Spring Data JPA 和 PostgreSQL。其关键设计要点如下：

-   实体设计：系统将订单、交易和持仓建模为 JPA 实体。例如，订单实体包含交易品种、账户、交易方向、价格、数量、状态和时间戳等字段。系统为交易品种、账户和状态创建数据库索引，以实现高效查询（例如，“查找账户 XYZ 的所有有效订单”）。
    
-   异步写入：为了避免阻塞交易线程，系统使用异步数据库操作进行持久化。例如，当发生交易时，撮合引擎会在单独的 Disruptor 环上发布一个 PersistTradeEvent 事件，供数据库工作线程使用。该线程可以在一个事务中批量执行多个插入/更新操作。这使得数据库 I/O 与交易处理解耦。
    
-   JDBC 调优：系统配置了 JDBC 驱动程序和连接池以实现高吞吐量。系统对交易和订单使用批量插入。此外，系统禁用了自动提交，并尽可能使用多行插入。大型对象（例如日志消息）根据需要存储在堆外或 NoSQL 数据库中（本设计中未使用）。
    
-   模式迁移：系统使用 Flyway 管理模式。每次部署都包含一个受控的迁移步骤，以便在应用程序启动之前可靠地应用模式更改（添加列或表）。
    

通过这些优化，持久化开销被降至最低。实际上，数据库写入最终与内存状态保持一致：崩溃或故障转移可能会丢失内存中最后几微秒的交易数据，但恢复后，我们可以根据需要从交易所日志中重放。这种设计确保交易不会因磁盘写入而延迟。
