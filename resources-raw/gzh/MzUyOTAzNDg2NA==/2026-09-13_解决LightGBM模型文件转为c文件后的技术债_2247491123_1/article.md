1.背景

在c++程序中调用lightgbm生产的模型做推理，开始使用的是lightgbm库。具体可参考官方文档（https://lightgbm.cn/en/stable/C-API.html）。

但是实盘后发现服务器上lightgbm库的线程有200多个，但处于运行中状态的及几个，给系统的资源分配带来问题。通过查阅资料设置参数也无果。

所以就把模型文件txt通过m2cgen工具转化为.c文件。

结果实盘用到的两个模型文件转化后最终为两个巨型C头文件：

-   `***.h`，172MB
    
-   `***.h`，177MB
    

里面是**m2cgen 风格的 if/else 决策树代码**：每一棵树就是一个巨大的嵌套函数，阈值全部内联在 `if/else` 分支里。原理就是模型的数据被当成了代码来编译。

这带来了三个致命问题：

1.  **编译几乎不可能**。GCC 要像编译普通代码一样处理这 349MB 的“数据”，还要生成调试信息，单次全量编译动辄数小时。
    
2.  **任何改动都触发全量重编**。因为两个巨型头文件被业务代码 `#include`，改一行业务逻辑也要把整个模型重新编一遍。
    
3.  **模型迭代成本极高**。换一次模型 = 换两个巨型头文件 + 再受一遍编译的罪。
    

比较尴尬的是，即使发现了这些问题，但当时大部分时间都在推进各家券商的实盘疲于奔命，也无暇真正的深究和解决这个问题，每次只能用一晚上时间编译。

## 当自此回看此问题是，其本质是数据与逻辑没有分离：

推理逻辑是固定的、很小的；模型数据是易变的、很大的。

两者一旦分离，编译和迭代的问题都会迎刃而解。

## 2.方案

**方案 A：模型数据与推理逻辑分离，运行时加载**

-   写转换器，把 if/else 树解析成数组结构：`{特征索引, 阈值, 左子树, 右子树, 叶子值}`
    
-   存为二进制文件，以我自己349MB的文本文件为例，生产的二进制几十MB
    
-   推理逻辑变成固定的小段代码（约 100 行）：树遍历循环，单线程，无依赖。
    
-   换模型 = 换一个 `.bin` 文件，零编译
    
-   启动时 `mmap` 加载，秒级。
    

**方案 B：拆分编译单元（如果实在不想改老代码）**

-   把转化的模型代码\*\*\*`.h`改成 `.cpp`，单独编译成静态库（`-g0 -O0`）
    
-   业务代码只 include 函数声明的小头文件，秒级编译
    
-   缺点：换模型时仍要重新编译那个巨型 `.cpp`
    

**方案 C：回归 LightGBM 原生 C API**

-   我前面背景中介绍了情况，虽然通过资料上都说通过 `num_threads=1` 可以解决，按我个人实际中怎么尝试都无果。
    
-   另外，从性能来说，原生C API的推理性能不如方案 A
    

所以在最新版本中，我修改成了方案A的方案，欠的技术债总算解决了。

## 3.实施与验证

转换工具链放在 `tools/` 下：

-   `***_model.cpp`：解析 if/else → 二进制
    
-   `model_verify.cpp`：验证转换正确性
    
-   `model_subset_test.cpp`：子集对比测试
    

产物：

-   可执行文件`编译不再依赖任何巨型模型头文件`
    
-   最终两个模型文件对应的二进制模型为：\*\*\*.bin（31M，4000 棵树 / 161 万节点）、\*\*\*.bin`（32M，4000 棵树 / 166 万节点）`
    
-   运行时通过 `mmap` 加载，启动时打印树/节点数量，加载失败返回 0 兜底（线程安全）

## 通过测试：

-   **编译时间**：从数小时降到业务代码秒级编译
    
-   **模型迭代**：换模型只需替换 `.bin` 文件，跑一遍 `model_verify` 验证，直接启动，无需重新编译
    
-   **部署体积**：不再携带 349MB 的巨型头文件
    
-   **启动性能**：`mmap` 加载，秒级启动
    

新的模型更新流程被简化成三步：

```
跑转换器替换 .bin 文件 → 运行 model_verify 验证 → 直接启动
```

## 小结

这次重构的核心，不是换框架，也不是调参数，而是**把“数据”从“代码”里请出去**。

当模型不再被当成代码编译，编译慢、迭代难、部署重的问题就一次性消失了。
