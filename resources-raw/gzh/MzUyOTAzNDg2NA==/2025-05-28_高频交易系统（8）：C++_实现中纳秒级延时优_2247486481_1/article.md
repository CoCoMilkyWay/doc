网络传输涉及到两个点：networking 和 concurrency。

就低时延传输来说：在高频交易（HFT）场景中，为最小化网络与系统延迟，通常采用**绕过内核协议栈**的方式直接从网卡接收数据（如使用 **DPDK、PF\_RING、XDP** 等用户态网络驱动），并将数据以零拷贝（Zero-Copy）方式分发到同一服务器上的多个进程（如策略计算、风控、订单路由等）。请注意，这些方法及投入适用于 **纳秒级延迟敏感** 的高频交易系统。

![](assets/002.png)

  

**以上方案的关键优化点包括**：

1.  **绕过内核协议栈**：
    

-   使用 **用户态网络协议栈**（如 DPDK）直接处理网络数据包，避免内核上下文切换和中断处理带来的延迟。
    
-   适用于 **纳秒级延迟敏感** 的高频交易系统。
    

3.  **零拷贝数据分发**：
    

-   数据通过 **共享内存（Shared Memory）** 或 **环形缓冲区（Ring Buffer）** 直接传递给本地进程，避免 `memcpy` 或系统调用开销。
    
-   结合 **内存映射（mmap）** 或 **IPC（如 Unix Domain Socket）** 实现高效数据共享。
    

5.  **多进程/线程协同**：
    

-   同一服务器上的多个进程（如策略引擎、订单管理、风险控制）通过 **无锁数据结构** 或 **原子操作** 高效协作，减少锁竞争。
    
-   可采用 **NUMA-aware 优化**，确保数据访问尽量在同一 CPU 核心上执行，减少跨 NUMA 访问延迟。
    

7.  **硬件加速**：
    

-   使用 **FPGA/ASIC** 加速网络包处理或策略计算（如订单匹配）。
    
-   结合 **RDMA（远程直接内存访问）** 实现跨服务器超低延迟通信（适用于分布式高频交易）。
    

  

再看原文之前，我们先了解下低时延网卡。

从网络带宽的角度，网卡分为1GE、10GE、25GE、40GE、100GE等不同带宽的网卡；从时延性能的角度，我们又可以把网卡分为普通网卡以及低时延网卡，在linux操作系统下，使用普通网卡做PingPong测试的回路时延大约在20微秒以上，而低时延网卡则在10微秒以内。证券行业比较有代表性的低时延网卡生产厂商有Solarflare、Mellanox、Exablaze、Chelsio等，这些网卡厂商首先提供低时延的标准内核网络协议传输能力，同时还通过各种加速技术，提供更加极致的时延性能。

二.共享内存

讲共享内存的文章很多。

共享内存是一种**进程间通信（IPC）**机制，允许多个进程直接访问同一块物理内存区域，无需通过内核进行数据拷贝。共享内存区域由操作系统内核创建和管理（如 Linux 的 `/dev/shm` 或 `shmget` 创建的共享内存段）。数据直接在进程间共享，无需额外的内存拷贝。

这里我想说下功夫开源的易筋经，虽然其采用的是mmap，但除了对底层做了封装外，主要是结合了实际的行情、交易定义及接口，在交易系统中应用起来更完善：

在易筋经中，首先为每个需要写数据的角色规定好属于他自己的一个写入单元（Journal），一个 Journal 只能有一个写入线程，从而保障它的进程/线程安全。

写入者 Writer 在写入内容时，每一次都是通过一个原子操作在 Journal 中形成一个 Frame。Frame 结构包含一个头部（Header）信息和数据部分，Header 中定义跟该次写入有关的一些元信息，例如写入时间，数据类型等。

数据部分的格式由数据类型定义，访问者利用元信息中的数据类型即可调用对应的解码器。这样，每一个 Journal 都可以看成由无数相邻 Frame 所组成的流式数据链。

但是由于底层使用 mmap 进行磁盘回写，而 mmap 本身只能创建定长文件，所以定义每次 mmap 创建的文件为 Journal 的一个页（Page），结构如下：

每个 Page 是一个定长的文件（目前在功夫中我们定义为 128MB 大小），易筋经会根据使用者需要进行拼接，使得访问者透明的得到一个无限长（当然，真正的容量上限取决于磁盘大小）的 Journal：

三.队列

作者先给出了一些队列设计关键点的思考：

![](assets/013.png)

视频中作者每个点都讲的很详细，下面一一大体解释下，具体细节还需要自己更深入的理解和实践：

Bounded?（有界性）

Yes – simpler & faster（有界 - 更简单且更快）：有界队列意味着它具有固定的容量限制。这种特性使得队列的管理相对简单，因为它不需要动态地分配大量内存来适应无限增长的元素。同时，由于内存使用是可控的，操作的执行速度通常也会更快，避免了因内存分配和扩展带来的开销。实际中我们要衡量：空间-时间，要么空间换时间，要么时间换空间。

Blocking?（阻塞特性）

No – readers don't affect the writer（无阻塞 - 读操作不影响写操作）。在并发环境中，如果一个队列是无阻塞的，那么读操作（消费者从队列中获取消息）和写操作（生产者向队列中放入消息）可以并行执行，彼此之间不会相互阻塞。这意味着写入者可以持续地将消息放入队列，而无需等待读取者完成读取操作；反之亦然，读取者也可以随时尝试从队列中获取消息，而不会因为写入者的操作而被阻塞。

Consumers?（消费者数量）

Many（多个）：该并发队列支持多个消费者同时从其获取消息。这在需要并行处理消息的场景中非常有用，例如在分布式系统中，多个工作线程或进程可以同时从同一个队列中读取任务并进行处理，从而提高整体的处理效率。

Message Size?（消息大小）

Variable length（可变长度），队列中的消息长度不是固定的，可以是任意长度。这种灵活性使得它可以适应各种不同类型和大小的数据，例如文本消息、二进制数据块等。在实际应用中，不同的业务场景可能会产生不同长度的消息，可变长度的消息支持能够更好地满足多样化的需求。

Dispatch?（调度方式）

Fan-out（扇出，翻译不确切），扇出调度方式意味着当有新消息进入队列时，该消息会被同时分发给所有的消费者。每个消费者都可以独立地处理接收到的消息，这种方式适用于需要将任务并行地分配给多个处理单元的场景，例如消息广播、事件通知等，比如收到行情后，分发道不同策略以及交易模块。

Type Support?（类型支持）

PODs（Plain Old Data types，普通旧数据类型），该并发队列只支持“普通旧数据类型”，即那些简单的、没有构造函数、析构函数、虚函数等复杂特性的数据类型，如基本数据类型（int、float 等）、结构体（struct）等。这种限制是为了简化队列的实现和提高性能，因为处理复杂的对象类型可能会引入额外的开销和复杂性，例如对象的构造和析构操作等。
