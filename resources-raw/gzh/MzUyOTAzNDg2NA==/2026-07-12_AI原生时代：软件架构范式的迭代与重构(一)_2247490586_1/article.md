# 1.Vibe Coding

就目前AI应用落地场景来看，AI编程场景无疑是见效最快、价值最稳的。代码融合了规范形式语言与人的自然表达，语法严谨、表意清晰，刚好契合大模型擅长处理的内容类型。

因此，我们必须认识到：

一个更深层的结构性变化正在发生：软件的生产方式本身正在被重构。

传统开发，人是“书写者”，程序员一字一行的敲代码，头皮屑飘落在油腻的键盘上，亲手把业务想法翻译成可运行程序。

AI 时代，编程不再是程序员的代名词，任何人都变成了需求阐述者，只需要讲清诉求，由 AI 产出代码，人再核对、敲定最终版本，代码不再靠逐行手写得来。

当ZHIHU推送了我：歌手胡彦斌进军 AI编程？他用 Vibe Coding 给粉丝造一个"彦火"APP社区。

# 2.转变

从单点看，AI会做产品需求分析，会出PRD文档，会做原型，会设计开发，会做单元测试，功能测试，是一个不折不扣的全栈六边形战士。

留给我们软件开发团队的难题是：如何来融入和组织这样的“AI生产力”。这个问题如果想不清楚，力图通过AI来替代程序员做降本增效都是冲动的决策。

因此，使用AI编程构建软件成为了一个绕不过去的命题。需要做好3大维度转变：

从开发管理工作角度，我们之前基于瀑布模式或敏捷开发等组织管理形式构建的软件开发管理流入或软件开发模式都需要发生革命性的转变。团队人员角色如何重新定义。

从开发技术栈角度，这一转变如多米诺牌一样，将会涉及到软件开发环节的每个层面，诸如：

-   AI原生架构的定义和标准？
    
-   对于管理型业务系统，是继续采用Java，还是采用Python？
    
-   在核心交易系统开发中，采用c++时在那个环节引入AI？
    
-   测试工作是否可以从软件测试自动化进化到AI自动化，这中间会有多大的增益？
    
-   自动化部署运维环节AI能否替代肉身的可靠性？
    
-   修改BUG的全流程是否交付AI来完成？
    
-   AI参与后的整个工作流及评审机制？
    
-   ......
    

然而，要完成AI时代的软件重新认识，必须对LLM、token，MCP，Skill，Agent，AI原生架构，这些基本概念和基本原理有一个深刻的理解和认识，并且自己一定要通过代码实践，因为这些概念是构成我们对AI时代软件理解的基本原则。

特别对开发团队来说，如果团队人员理解参差不齐，那做一个新功能设计时，到底做成skill，还是做成agent，skill中应该包含哪些内容，不包含哪些内容，agent应该如何设计，包含什么功能边界，agent中如何管理大模型token的调用，等等。就很难讨论出来。

# 3.大模型

我们逐层拆解AI技术体系，先从最核心的底层根基说起。

整个AI技术浪潮的核心底座是LLM，也就是大语言模型。

目前市面上绝大多数主流大模型，核心训练框架都依托Transformer架构搭建。这套架构的技术原理看似晦涩复杂，不用深究细节，我们只需记住：它是所有大模型的核心底层引擎。

Transformer架构由谷歌团队在2017年正式提出，配套的经典论文《Attention Is All You Need》奠定了现代大模型的技术基础。颇具行业趣味的是，谷歌点亮了这项核心技术的雏形，却并未将其发扬光大，反而是由OpenAI先将这项技术落地深耕，引爆了全球AI变革。

2022年末问世的GPT-3.5，是首个真正实现规模化落地、具备实用价值的大模型，让大众和行业真切感受到人工智能的实用能力。时隔数月，2023年3月发布的GPT-4，再度突破技术上限，大幅拉高了通用AI的能力边界。可以说，GPT系列是本轮人工智能产业化浪潮的源头与标杆。即便到了现在，迭代后的GPT系列模型，依旧稳居行业第一梯队，是业界公认的顶尖水准。如今的AI行业早已告别单一玩家垄断的格局，Claude、Gemini等一众优质模型快速崛起，在不同应用场景中强势突围，与GPT系列形成同台竞争、百花齐放的行业格局。

前面讲完大模型的起源，再拆解它的运行逻辑，道理其实很简单，可以简单的理解为：不停续写句子。

举个生活化的例子，在大模型对话中输入提示句：傍晚去海边散步。

模型接收文本后，内部计算筛选出概率最高的下一个词，例如海风。

重点在于，模型输出这个词不会终止运算，而是把「海风」拼接在原有句子后方，形成新文本：傍晚去海边散步海风。

再用这段全新内容预测下一个词汇，比如微凉；再次拼接得到：傍晚去海边散步海风微凉。

循环往复，持续追加新生成的词语，直到模型判断整段语句逻辑完整，自动生成终止标记，停止输出。

最终完整回答就是：傍晚去海边散步海风微凉。

这就是大模型最基础的生成逻辑，它逐字逐句缓慢吐出内容的原因，每一个字都依托前文重新推算得出。

# 4.Token

前面我们讲到，大模型回答问题是逐词生成的。但这其实是简化后的直观效果。真正的底层逻辑并不是“处理文字”，而是纯数学运算。大模型本质是一个巨大的函数，全程只认识数字、矩阵，完全看不懂人类的文字。我们先看OpenAI官方的解释：

文本生成、文本嵌入两类模型处理文字时，都会先把文本切分成最小单元 :词元（token），词元本质是模型归纳出的高频字符片段。

举个例子，英文单词 tokenization 会拆成 token、ization 两段词元；the 这类简短常用词，则单独作为一个完整词元。另外句子里多数单词的首个词元，前面都会自带空格。

大家可以打开 OpenAI 官方分词工具链接，输入任意文字，直观查看文本是如何拆分为词元的。 常规换算标准：一个词元平均对应 4 个字符，折算英文约 0.75 个单词。

这里有一条关键限制：

文本生成模型：用户输入提示词 + AI 生成的全部内容，两者词元总数不能超出模型最大上下文窗口；

词嵌入模型（不会生成新文本）：仅输入文本的词元长度，就必须小于模型上限。

各款生成、嵌入模型对应的最大上下文长度，均可在 OpenAI 开发者文档的模型介绍页面查询。

# 5.Tokenizer

所以在用户和大模型之间，必须有一个“翻译官”，这个角色就是Tokenizer。

它只做两件核心的事：编码和解码。

编码是把文字转成数字，送给模型运算；

解码是把模型输出的数字，重新变回人类能看懂的文字。

我们先看编码全过程，分为两步：

第一步是文本切分。Tokenizer 会把我们输入的一整段话，拆成一个个模型能处理的最小文本单元，这些最小单元，就叫做Token。

第二步是数字映射。每一个 Token 都会对应一个唯一的数字编号，这个编号就是Token ID。文字变成 Token、Token 映射成数字，人类的句子，就成功转换成了模型能读懂的数字列表。

模型接收这串数字列表后，经过复杂运算，会输出一个新的 Token ID。这时就轮到解码工作了。

解码过程很简单，只需要反向映射，把输出的数字重新翻译回对应的 Token，就得到了我们看到的文字。

如果句子还没生成完整，模型就会循环这个过程，持续输出，直到语句结束。

通过上面可以看到Tokenizer 的切分规则是模型自主学习的，和我们人类的分词习惯完全不一样。Token 是大模型处理文本的最小单位，和日常词语没有一一对应关系。而支撑这套 Token 切分规则的核心，就是 BPE 算法，也是整个 Tokenizer 的底层原理。

# 6.Context和Context Window

开发同学对这个概念应该不会陌生。

前面我们弄懂了token，它是大模型处理文字的最小单元。

这里有个很多人疑惑的点：和AI聊天时，它总能记住我们之前说过的内容，比如你先说自己叫张三，隔几句再问它你的名字，它能准确答出来。 但大模型只是一套数学运算函数，本身不存在人类意义上的记忆，它是怎么留存对话信息的？

原理很简单：每次发送新提问时，程序会自动把全部历史对话拼接在一起，和当前问题一并传给模型。模型每次运算，拿到的是完整全程对话，自然能关联前文内容。

这就引出了上下文（Context）：指模型单次运算时接收的全部信息总和。

用户提问、过往聊天记录都属于上下文；

模型实时生成的每一段token、系统提示词、可用工具清单等内容，也都会纳入上下文。

简单来说，上下文就是大模型的临时存储空间。（PS：对投资同学，关心的存储也与此处有关联。）

明白上下文之后，新问题随之而来：这份临时存储最多能承载多少内容？容纳token的上限由上下文窗口决定，它代表上下文最多可承载的token总量。

举个例子，上下文窗口容量10000，就意味着模型单次最多处理一万个token，这个尺寸放在当下只能算偏小。

现在主流大模型都配备超大上下文窗口：GPT 5.4支持105万token，Gemini 2.5 Pro、Claude Opus 4均为100万token。 按照1个token约对应1.5个汉字换算，100万token大约等效150万字，足以完整收纳全套《哈利波特》，存储能力十分可观。

如果在工作中涉及到这点，则选择上下文窗口不能一味追求更大，要结合业务场景、调用成本与响应速度综合判断。

比如日常单次问答、小段代码调试等轻交互场景选用 4k/8k 小窗口，成本低、推理更快；

多轮对话、数千字文档处理等常规办公开发需求适配 32k~128k 中等窗口；

完整文档、全量代码库、百万字文稿通读等必须加载全部资料的场景，再选用百万级超大上下文，同时可搭配向量数据库做分段检索减少长文本输入，降低开销与延迟，使用时还需预留两成 token 余量防止内容截断，日常优先中小尺寸，超长任务临时切换大窗口即可平衡体验与费用。

测算不同上下文窗口使用成本，核心以 token 为计量单位，先统计单次请求全部输入 token（包含系统提示词、历史对话、参考文档、当前提问，总量不能超过所选模型上下文窗口上限）与模型生成的输出 token，再套用基础公式：

单次费用 = 输入 token 总量 × 百万输入单价 ÷1000000 + 输出 token 总量 × 百万输出单价 ÷1000000；

超大上下文模型常设置阶梯定价，输入 token 超过阈值会触发输入、输出双重涨价，多轮对话重复上下文可启用前缀缓存降低输入单价，同时窗口越大单次输入 token 基数越高、算力开销呈平方级上涨，长期高频调用成本差距会显著拉大，测算时还可先用官方 tokenizer 工具把文本换算为精确 token 数，结合日均调用次数算出月度总开销，对比不同窗口规格的综合成本后再做选型。
