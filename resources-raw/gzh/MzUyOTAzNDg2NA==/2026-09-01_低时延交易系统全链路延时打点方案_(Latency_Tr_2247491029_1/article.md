目标：在不影响报单关键路径延时的前提下，为高频交易系统"行情SDK-行情-因子-模型-策略-风控-报盘-柜台sdk-交易柜台"全链路的每个节点增加可开关的延时测试能力，定位各段耗时瓶颈。

## 1\. 背景与核心约束

本系统是一条跨6个线程域、由3处队列/线程池解耦的异步流水线，而非单线程同步执行。

因此打点方案的第一原则是：时间戳必须随数据一起流动（不能用线程局部变量），并且打点动作本身必须极轻（只读时钟 + 写字段）。

从系统设计侧考虑，核心设计原则包括：

-   默认零开销：不开启时对报单路径无任何影响。
    
-   可选开启：编译期可裁剪 + 运行期可开关（双开关，已确认）。
    
-   不污染关键路径：打点只做"读时钟 + 写字段"，不加锁、不 I/O、不 malloc；统计/落盘走独立后台线程旁路。

## 3\. 关键技术选型

### 3.1 时钟源：两种方案的详细说明

打点方案有两种候选时钟源。

两者都可以封装成统一接口 now\_ticks() 和ticks\_to\_ns()，业务打点代码只调这两个函数，切换实现时业务代码不动。

方案A：clock\_gettime(CLOCK\_MONOTONIC) / std::chrono::steady\_clock

内核维护一个自开机起单调递增的纳秒计数。Linux 通过vDSO把该读取映射到用户态，clock\_gettime 在大多数情况下不陷入内核（不是真正的 syscall），直接在用户态读共享内存页里的时钟数据。std::chrono::steady\_clock 在glibc上底层就是 CLOCK\_MONOTONIC。

优点：

-   无需标定：返回值直接是纳秒单位，拿到就能相减，不用测频率。
    
-   单调可移植：跨核一致（内核已处理同步），不受 CPU 变频、NTP 调时影响；换机器/换 CPU 无需改代码。
    
-   精度足够：分辨率 1ns，单次读取开销约 15–30ns。本系统各段耗时（排队 + 因子 + 推理）都在微秒到毫秒量级，20ns 的测量误差占比 <0.1%，完全看得清瓶颈。
    

缺点：

-   相比 rdtsc 有约 20ns 的固定开销。对"看清各段占比"无影响；但若要测的是纳秒级微优化本身（例如某段只有 50ns，想优化到 40ns），20ns 的测量开销就会干扰结果。
    

代码：

```
inline int64_t now_ns() {
```

方案B：rdtsc（Read Time-Stamp Counter）

CPU 内部有一个硬件寄存器 TSC，每个时钟周期自增。rdtsc 指令直接读它，返回的是周期数（cycles）而非时间，需除以 TSC 频率（GHz）才换算成纳秒。

优点：

-   开销最低：单次约 20–30 个 CPU 周期（~6–10ns），是所有时钟里最快的，是 HFT 里测纳秒级路径的标准做法。
    

缺点（均为需额外处理的工程成本）：

-   必须标定频率：TSC 只给周期数，启动时要跑一段"读 TSC + `clock_gettime` 对拍"来测出每 ns 多少 cycle；测不准则所有时间换算都偏。
    
-   跨核漂移风险：不同物理核的 TSC 起点可能不一致。本系统链路跨 4 个线程域，很可能跨核——T0 在核 A、T5 在核 B，两核 TSC 不同步会算出负延时或虚高延时。规避方式：绑核（taskset / pthread affinity），或确认 CPU 具备 `constant_tsc + nonstop_tsc + TSC 同步` 特性。
    
-   乱序执行干扰：`rdtsc` 可能被 CPU 乱序提前/延后执行，严谨时要用 `rdtscp` 或加内存屏障（`lfence`），否则测量点会漂。
    
-   变频/睡眠影响：老平台上 TSC 会随 CPU 变频而变速。现代平台若为 `constant_tsc`（恒频）可放心，需 `cat /proc/cpuinfo | grep -E 'constant_tsc|nonstop_tsc'` 确认。
    

代码：

```
inline uint64_t rdtsc() {
```

实践：

在高频交易系统的全链路延时打点方案中，我们面临时钟源选型：rdtsc（硬件级，~6-10ns）还是 steady\_clock（vDSO，~15-30ns）。

硬件条件上，使用的AMD EPYC 7K62（128核）已确认支持 constant\_tsc + nonstop\_tsc + rdtscp，rdtsc 的硬件前提是满足的，但第一次改还是选择 了steady\_clock方案。

考虑的依据是测量目标与工程代价的匹配。

我们的目标是定位跨线程链路的微秒~毫秒级瓶颈段（队列排队、因子计算、模型推理），而非优化某个 20ns 的指令序列。steady\_clock 约 20ns 的单次开销，在微秒级测量目标下误差占比 <0.1%，完全足以看清瓶颈分布。rdtsc 的极致低开销优势，在这个测量精度需求下是"过剩性能"。

更大的考量在工程层面。

链路跨多个线程域、128 个大核，线程池里的 worker 天然可能跑在不同物理核上。rdtsc的跨核 TSC 漂移问题意味着必须先做 CPU 绑核规划和亲和性配置：这不仅增加实施复杂度，更关键的是绑核会改变现有线程调度行为，可能直接影响报单路径本身的性能特征，与我们"不影响关键路径"的第一约束直接冲突。而不绑核直接上 rdtsc，则可能产出负延时或虚高数据，污染统计结果，排查成本极高。

因此综合考虑后第一阶段的计划是：用 steady\_clock 快速落地、数据可信、零额外工程成本；同时将时钟源封装为 now\_ticks() / ticks\_to\_ns() 两个内联函数，业务打点代码只调接口不碰实现。二期若要切 rdtsc，只需改这两处封装，所有埋点代码零改动，把硬件级时钟的复杂性"隔离"在封装层后面，不扩散到整个系统。

### 3.2 打点载体：字段内嵌

在跨线程流水线中，时间戳必须随数据流动，因此我们选择字段内嵌方案：在跨线程传递的核心数据结构中直接嵌入打点数组，终点一次性算差值，无需按 seq 归并，归并成本为零。

关键约束是行情原始结构 snapShotStruct 带有 #pragma pack(1)，且参与 parse、落盘、回放等多处逻辑，改动风险最高，因此不动它。但为了覆盖"行情回调入口 → 报单发出"的完整链路，又必须拿到行情到达时刻。我们的做法是函数参数透传：在行情回调入口处取一次 now\_ticks()，沿 parse\_market\_data → verify → dispatcher 调用链通过新增参数逐层透传，最终在因子引擎构造 HftFactorData 时写入其内嵌的 LatencyTrace。这样只改了少量函数签名，完全避开了对 snapShotStruct 的侵入。

对于其他载体，HftFactorData 是普通 struct，直接新增打点数组；HFTSignal 虽也带 pack(1)，但将打点数组放在结构体末尾并用编译开关隔离，最大程度降低 ABI 影响。整体原则是：让时间戳跟着数据走，但不污染既有序列化布局，能改的 safe 结构直接加字段，风险高的结构用透传绕开或末尾追加。

### 3.4 双开关设计（已确认）

编译开关：

-   关闭：`LatencyTrace` 字段与所有打点宏均不编译进去 → 结构体不增大、路径零指令，真正零开销。
    
-   开启：字段与打点代码编译进去。
    

运行开关（atomic g\_latency\_on，由配置项 \[latency\] enable=0/1 初始化）：

-   即使编译进去，运行期 `enable=0` 时打点宏内部 `if (unlikely(!g_latency_on)) return;` 直接跳过，仅一次分支判断的固定开销。
    
-   生产可灰度：先编译进去、默认运行期关闭，需要时热态观测（若支持信号/命令切换）或改配置重启。
    

打点宏形态：

```
#ifdef HFT_LATENCY
```

### 3.5 上报旁路（关键路径零 I/O）

打点数据的关键路径旁路策略是：在报单发出前的最后一个打点节点，将完整的延时轨迹（LatencyTrace，栈上小结构，值拷贝）直接放入一个无锁队列（如 moodycamel 实现）中，入队操作仅耗时数十纳秒。

一个独立的后台聚合线程从该队列消费数据，在线程内完成直方图累加（采用 HdrHistogram 风格分桶或简单固定分桶）、统计计算和落盘输出，整个过程中关键路径线程不触碰任何 I/O、锁或内存分配操作。

聚合线程定期（如每分钟）或进程退出时，将各段延时的 p50/p90/p99/max 等统计指标输出为 CSV 或 Markdown 报表。这一设计的核心原则是：打点只做"读时钟 + 写字段"，统计和落盘全部旁路到后台线程，确保对报单主路径的零干扰。
