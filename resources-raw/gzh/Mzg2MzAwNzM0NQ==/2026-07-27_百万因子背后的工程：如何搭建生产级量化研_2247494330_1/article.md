> 本文主要介绍了可落地的生产级量化 Agent 架构，涉及数据、计算、缓存、评估与反馈等关键环节，干货较多，建议完整阅读。

大模型可以高效生成一段因子代码，但代码数量并不等于研究产能。候选因子增加后，数据口径、时间对齐、缓存复用、交易约束和结果追踪会逐渐成为主要问题。如果这些工作仍由每段临时 Python 代码自行处理，系统能够产生很多回测，却很难形成可复用的生产级别的因子库。任务运行时间进一步延长后，还会遇到缓存失效、数据更新、进程中断和重复研究。

因此，本地量化研究Agent的重点不在模型本身。它需要一套独立于模型的研究架构，把数据、计算、验证、反馈和状态管理固定下来。核心的点在于AI负责提出假设、选择字段和组合算子，数据对齐、因子计算、交易约束及评估由本地确定性程序完成。

## 一、Agent职责划分

量化研究中既有开放问题，也有确定性问题。因子假设、字段选择和研究方向可以交给Agent，数据对齐、表达式执行、标签计算和交易约束则应由固定程序完成。

一个相对清楚的结构如下：

```
Research Agent  ├─ 提出假设  ├─ 选择字段和算子  ├─ 解释结果  └─ 决定下一轮研究          │          ▼Tool Layer  ├─ 数据查询  ├─ 因子编译与执行  ├─ 因子评估  └─ 状态与报告          │          ▼Research Core  ├─ Data Catalog   ├─ Operator Engine  ├─ Cache / Incremental Compute  ├─ Evaluation  └─ Research Memory
```

这套划分会限制Agent的执行权限，研究结果更容易复现。模型升级或更换以后，底层数据和回测口径仍然保持不变，同一个候选也可以重新计算。

## 二、存算分离

行情、财务和分钟数据适合使用Parquet等列式格式长期保存，研究阶段则更适合转换成`date × sid`矩阵。长表便于查询和增量写入，矩阵适合重复执行时序、截面和掩码计算。

以5000只股票、2500个交易日为例，一个`float32`字段大约占50MB。日频收盘价、成交额、市值、行业和交易状态可以通过按需加载、内存映射及紧凑类型放在单机上计算。候选数量增加后，主要成本来自重复读取数据和重复计算公共节点，不单单和因子数量成正比。

从具体实现来看，Polars、DuckDB、NumPy和Cython分别适合不同环节。DuckDB用于数据发现和临时查询，Polars负责列裁剪与批量清洗，NumPy承担矩阵计算，Cython用于自定义滚动窗口以及循环处理。试图用一个框架完成全部工作，通常会在查询效率或计算效率上有所损失。

多频数据统一时，需要统一的是可用时间和调用规则。财务数据应当按公告时间进入交易轴，分钟数据则应先加工成稳定的日内特征，再进入日频因子接口。直接把多个频率的数据拼成宽表，时间对齐和管理会比较困难。

## 三、Harness核心

在候选数量较少时，AI直接编写Python可以较快完成想法验证；当研究范围扩大到十万乃至百万级候选后，这种方式的缺点会逐渐显现。

每段临时代码都可能采用不同的数据处理规则，例如调整样本范围、填充缺失值，或者使用错误的`shift`方向。此类问题未必导致程序报错，却会改变因子值和回测结果。仅通过提示词要求模型避免未来函数，无法形成稳定约束。

例如，一个简单的因子可以写成：

```
cs_zscore(ts_return(close, 5))
```

这段表达式先计算过去五日收益，再进行截面标准化。Agent可以调整字段、窗口和算子组合，底层数据处理仍由Harness统一完成。相比自由Python，DSL保留了因子的计算结构，也缩小了需要检查的范围。

更可行的方式是设计一套受限因子表达式DSL。Agent只能使用已经登记的字段、算子和参数，表达式在运行前完成语法检查、字段检查、窗口检查、依赖提取及回看长度推导。未知函数、任意属性访问和没有字段依赖的表达式直接拒绝。

DSL进入系统后，还需要经过一次编译。编译器先把不同空格和写法转换为标准表达式，再生成抽象语法树，提取`close`和`industry`等依赖字段，推导五日回看窗口，最后形成可执行计划和稳定身份。批量候选中如果多次出现`ts_return(close, 5)`，系统可以识别为同一个中间节点，只计算一次。

工具接口同样需要保持稳定结构。一次调用应当区分正常结果、警告、错误和生成产物，批量任务还要记录失败候选的序号、表达式和错误类型。Agent获得结构化错误后，才能据此调整参数、替换字段或终止当前研究方向。

## 四、单机处理百万因子

百万级候选不适合按照百万个独立脚本执行。多数因子会反复使用收益、成交额、市值、中性化结果和不同期限的未来收益，系统应当一次加载同批候选依赖的字段，并复用公共中间表达式。

缓存可以分为四层。数据矩阵缓存保存行情、财务字段和交易状态；中间表达式缓存保存滚动收益、均值和排名等DSL公共节点；因子缓存保存最终的`date × sid`矩阵；评估缓存保存未来收益、IC、分组收益和换手等结果。

缓存身份不能只由表达式决定，还要包含数据版本、股票池、时间口径和执行策略。同一个表达式用于不同股票池时，应当形成不同的因子结果；基础数据发生历史修订后，相关缓存也需要失效。

读取缓存时还应检查日期轴、证券轴、矩阵形状和运行元数据。文件存在只能说明系统曾经生成过结果，不能说明该结果仍适用于本次研究。校验失败后重新计算，会增加一定时间，但能够避免旧数据进入新的回测。

增量计算需要保留明确的回退条件。交易日向后追加且历史数据没有变化时，可以复用原有因子值，只计算受新数据影响的区间；基础字段发生修订后，应从最早变化位置结合因子回看长度重新计算；证券轴或数据版本无法安全对齐时，则需要执行全量重算。

因此，单机处理百万因子首先是计算复用问题。实际吞吐量还取决于字段数量、算子复杂度、股票池、样本长度和缓存命中率，需要在统一Benchmark下进行比较。

## 五、研究记忆

context不能替代研究记忆。完整AI对话记录包含大量重复描述和临时输出，对下一轮因子研究帮助有限。

研究系统需要保存候选表达式、数据版本、评估摘要、接受或拒绝状态、相关性、失败原因和变体来源，同时区分样本内结果、样本外结果及研究员判断。某类高换手因子连续失败后，Agent下一次启动时应当能够看到这段记录，减少重复计算。

长任务还需要及时保存状态。单个候选完成后写入结果，批次中的局部失败不影响其他候选，文件采用原子方式更新，进程重启后根据已完成状态继续运行。独立调度器、worker心跳、超时、重试、资源监控和任务级checkpoint，则决定系统能否稳定运行数天。

生产级系统无需依赖单个进程持续存活。更重要的是在进程退出后，系统仍能识别已经完成和尚未完成的任务，并从正确位置恢复。

## 六、评估体系先于自动挖掘

Agent能够快速产生候选，因此更容易放大数据挖掘偏差。因子评估至少应统一数据可用时间、股票池、信号滞后、未来收益、停牌和涨跌停规则，并同时观察IC、ICIR、分组收益、换手、成本后收益、覆盖率及风格暴露。

候选数量较多时，可以先做低成本筛选，再对保留因子进行相关性、分年度稳定性和走样本外检验。最终结果还应与已有因子比较，判断新增信息是否只是旧因子的另一种表达。

漂亮的历史净值不能替代这套流程。回测条件发生变化后，收益数字本身没有稳定含义。

## 七、AxiomQ.Factor

最后再介绍下AxiomQ.Factor，这是我们AxiomQ系统中的Factor Agent模块，基于上述架构的本地实现。当前系统已经实现高频量价，财务数据以及另类数据的自动挖掘，使用矩阵存储、受限因子表达式、批量执行、缓存、增量计算及本地研究知识库。系统可以记录候选的评估结果、相关性、接受和拒绝状态，并在任务中断后保留已完成研究。

AxiomQ.Factor的因子假设可以来自Agent不断学习过程中的自我进化，也可以从AxiomQ.Paper模块学习研报/论文，最终生成的因子提供给AxiomQ.Model，用户也可以使用自己的股票池、风险模型和组合方式构建相应组合。

## 结论

搭建本地量化研究Agent，因子挖掘只是其中一部分。数据处理、受限工具、矩阵计算、缓存、研究记忆和样本外验证，共同决定系统能够产生多少可信结果。

AxiomQ.Factor在持续研究过程中，结合我们之前的系统，已经积累了一批综合**评价很高**，并与传统因子**低相关性**的因子。这些因子适合已经具备基础数据和组合系统，但希望补充低相关信号、提高因子研究效率的量化团队。AxiomQ.Factor的使用相对自由，可以接入用户自己的组合优化模块。
